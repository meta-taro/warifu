## 先に言う — **4 は D31 と正面からぶつかる**

**「自由入室」は、割符を持たない相手を通すということである。**

`decisions.md` **D31** は「知らない相手は人に取り次がずに断る」と決めた。
理由は spam ではなく **「通知を出せること自体が資源」**だからで、
**D12**（割符で相手を確定する）と対になっている。
2026-09-02 には、この 2 つが実装から抜けていたのを見つけて塞いだ（**D39**）。

**自由入室を入れるなら、その塞いだ穴を意図的に開けることになる。**

### 案 — **公開しても壊れない鍵を、別の種類として作る**

オーナー指示（2026-09-03）:「**割符を公開するなどして対応する策**」。

**いまの割符は一度しか使えない**（D12「一度使った割符は二度使えない」・`Tally::match_half` が
`used_by` を立て、二度目は `AlreadyUsed`）。**公開する鍵は何度も使えないと成立しない。**

**混ぜてはいけない。**同じ型に多用を許すと、個人に渡す割符の一回性まで崩れる。
**別の種類として作る。**

| | 割符（`Tally`・既存） | **会場鍵**（新規） |
|---|---|---|
| 渡し方 | 人が 1 人に渡す | **公開する**（貼る・載せる・読み上げる） |
| 使える回数 | **1 回** | **何度でも** |
| 期限 | 短い（既定 10 分） | 会期に合わせる |
| 失効 | 割符 id 単位 | **会場鍵 id 単位**（切れば以後の入場が止まる） |
| 戸口の答え | `Open` | `Open`。ただし**「会場鍵で来た」と印が付く** |

### 公開しても失われないもの

**誰が入ったかは分かる。**会場鍵は「入場してよい」ことしか言っておらず、
入る側は**自分の端末鍵で署名した片割れ**を出す（`Acceptance`）。
**鍵が公開でも、入場者の身元は 1 人ずつ確定する。**

これが**出禁を可能にする土台**である（下の 8）。

### 会場鍵で壊れるもの — **注意の資源**

D31 が守っていたのは spam ではなく「**知らない相手がこちらの注意を消費できないこと**」だった。
**会場鍵を公開した瞬間、そこは開く。**だから会場鍵には**必ず**次を付ける。

- **戸口の回数制限**（`warifu-door` の Rate Limit・D31 で既に実装済み）
- **待合室の上限**（並べる人数に天井を置く。超えたら**黙って落とす**）
- **会場鍵の失効**（漏れた・荒れたら切る。切ると以後の入場だけが止まり、**中の人は残る**）

**「公開する鍵を作る」ことと「注意を無防備にする」ことは別**である。ここを分けて設計する。

## 8 — 許可制（待合室）。**目的は 2 つある**

オーナー指示（2026-09-03）:
「**出禁・再入室を防ぐ**ため」と「**入室までの内輪話**をして、客がいきなり入らないようにするため」。

**目的が 2 つあると、必要なものも 2 つになる。**

### 8-a. 出禁 — **会議ごとの締め出しにする。失効と混ぜない**

`warifu-core` の `Revocations` は**取り消せない**（D12）。
端末鍵を失効させれば確かに二度と入れないが、**誤操作が永久に戻らない。**
**キックの押し間違いで、その人の端末鍵を恒久的に殺すのは釣り合わない。**

| | 会議ごとの締め出し（**推す**） | 端末鍵の失効 |
|---|---|---|
| 範囲 | その会議だけ | **warifu 全体** |
| 取り消し | できる | **できない**（D12） |
| 使う場面 | 荒らし・誤って入った人 | **鍵を盗られた**とき |

**キック＝会議ごとの締め出し。**会議が終われば消える。
`Revocations` は**鍵を失った場合のためだけ**に残す。

### 8-b. 内輪話 — **開場という状態を持つ**

「客がいきなり入らないように」は、許可を 1 人ずつ出す話ではなく、
**まだ開けていない**という状態の話である。

- 会議は **開場前 / 開場中** を持つ
- **開場前**は、会場鍵を持つ人も待合室に並ぶ
- 主催（または運営権限を持つ人）が**開場**を押すと、並んでいた人がまとめて入る
- 開場後は、既定で**素通し**（1 人ずつ許可しない）

**1 人ずつ許可する形も選べるようにするが、既定にはしない。**
既定にすると、主催は会議中ずっと戸口を見ていることになる。

### D31 と両立するか

**する。**並ぶのは**鍵を持っている相手だけ**である。
鍵を持たない相手は待合室にすら現れない（戸口が黙って落とす）。
D31 が禁じたのは「**鍵を持たない相手**が『通しますか』を出せること」だった。

## 9 — 予定を外のカレンダーへ入れる

オーナーの位置づけ（2026-09-03）:
「**スケジュール管理を Apple や Backlog など別に主体で持っている企業が、
試しに warifu を使い始めるために必要な妥協機能**」。

**その目的なら `.ics` が本命であって、妥協ではない。**

### なぜ 1 社の API より広く効くのか

`.ics`（iCalendar / RFC 5545）は**そこに挙がった全部が取り込める**。

| 相手 | `.ics` | 専用 API |
|---|---|---|
| Google カレンダー | ✅ | Google のみ |
| Apple カレンダー | ✅ | Apple のみ |
| Outlook / Microsoft 365 | ✅ | Microsoft のみ |
| Backlog・Notion・Slack ほか | ✅（取り込み口を持つものが多い） | それぞれ別に作る |

**「試しに使い始める」相手の環境は分からない。**1 社の API を選ぶと、
**そこに居ない会社は最初から試せない。**`.ics` なら 1 つ作れば全部に入る。

### `.ics` でできること・できないこと

| | |
|---|---|
| **できる** | 予定を作る／**変更を反映する**（同じ `UID` と `SEQUENCE` を上げて渡し直す）／取り消す（`METHOD:CANCEL`） |
| **できない** | 相手のカレンダーを**読む**こと。双方向の同期 |

**読む側は `warifu-calendar`（D26）が既に持っている** —「**空いているかだけを出す**」形で、
予定の中身は外へ出さない。**書き出す側を `.ics` にすれば、読み書きの両方が埋まる。**

### 決めたいこと

- **`.ics` の書き出しを先に入れる。**アカウント不要・追加依存なし（テキストを 1 本組むだけ）
- **専用 API はここでは採らない。**採るなら「PRD の『アカウントを作らない』を
  会議機能については外す」という決定が要る。**`.ics` で足りないと分かってから**でよい
- 会議の題・説明文を `.ics` に入れるかは、**招待に題を含めるか**（下の 5）と同じ判断

## 6 と 7 — キックと権限の委譲

**キックは「誰がやってよいか」の問題**であり、`warifu-capability`（**D24**）の担当である。

- **主催者だけ**なら実装は小さい（名簿は主催者を知っている）
- **委譲する**なら「A が B に運営権限を渡した」を検証できる形が要る。
  これは**委譲の連鎖**であり、`issues/001` が「**UCAN 1.0 が上位互換**」と結論した領域そのもの

### 先に決めること

1. **委譲を自前で作るか、UCAN に寄せるか**（`issues/001` の宿題がここで発火する）
2. **キックは何を意味するか** — その会議から出すだけか、**割符も失効させる**のか。
   失効させるなら**取り消せない**（D12）ので、誤操作が戻せない
3. **キックされた側に理由を返すか。**D31 は「断る理由を分けない」と決めている

## 5 — 題・日程・説明文

**日程は `warifu-calendar`（D26）と `issues/005` の Phase 3 に既にある。**
D26 は「**空いているかだけを出す**」と決めており、予定の中身は外へ出さない。

**題と説明文は「中身」である。**会議の名前を相手へ渡す時点で、
**それは暗号化された経路の上を流れるが、名簿に載る全員が読める。**
そこまでは自明だが、**招待の文字列に題を含めるかは別**である。

- 含めると、**割符を渡すだけで題が漏れる**（紙に書いた時点で読める）
- 含めなければ、入るまで何の会議か分からない

**含めない**を既定にしたい。**決めるのはオーナー。**

## 2026-09-04 — **会議キーが「開始」を持つようになった**（**D43**）

オーナー指示:
> 会議キーはスケジュール機能ついたら、**開始、終了期限**でないといけないです。

**割符には期限（`not_after`）しか無かった。**「来週の火曜 10 時から」の鍵を前もって
配ると、**渡した瞬間から入れた。**予定に紐づけた時点で、期限だけでは足りない。

`not_before` を足した（署名の中に入る）。`--from` / `--until` で指定する。

```
$ warifu host --from +3600 --until +7200
（開始前に入ろうとすると）warifu: まだ始まっていません
```

### 会場鍵（このイシューの本題）との関係

**会場鍵は「何度でも・数か月」だが、それでも「いつからいつまで」は要る。**
D43 で入った窓は、会場鍵にもそのまま効く。

残っているのは会場鍵の側 ——

- [ ] 何度でも使える（いまは D12 で 1 回きり）
- [ ] 失効の口を画面に出す
- [ ] 会場鍵と個人の割符を、画面で別のものとして見せる

### 併せて直した不具合

**開始前に 1 人叩いただけで、主催（`warifu host`）が落ちていた。**
割符に合わない相手が来ると待ち受けごと終わる作りだった。
**予定に紐づく鍵では致命的**（会議が始まる前に主催が居なくなる）。

主催は待ち直すようにした。終わってよいのは**鍵が切れたときだけ。**
