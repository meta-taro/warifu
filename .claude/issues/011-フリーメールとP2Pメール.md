## どこから来た要望か

2026-09-06 のオーナー指示（要旨）。

> 企画にあると思いますが、**フリーメールも作りたい**です。
> **なんらかのドメインを OSS ですが取る**ので、**ソフト側に Postfix みたいのを持つか、
> P2P メールを実現したく。**

## 先に言う — **ドメインを取ることは、記録済みの決定に当たる**

`PRD.md` **§12-3** が、同じ提案（企画書 §5 §6「共通ドメイン ＋ 中央 Directory」）を
**「採らない」と決着させている。**理由は 3 つ、全部そのまま生きている。

| | |
|---|---|
| **名簿が探索可能になる** | **それが Sybil 耐性の根拠**だった（探せない相手には、大量になりすます意味が無い） |
| **運営側に責任が発生する** | Abuse・SPF / DKIM / DMARC・domain reputation。**企画書 §25 §26 が自分でそう書いている** |
| **思想と逆を向く** | §0-0（中央のサーバー費用を誰かが払う構造を置き換える） |

**ただし §12-3 は抜け道も書いている。**

> **要点は「中央を置くか」ではなく「その中央が探索可能な名簿を持つか」。**
> 復旧だけを担い、**問い合わせても他人を探せない**形なら、Sybil 耐性を落とさずに解ける可能性がある。

**ここが、この Issue の争点である。**

---

## 技術の事実（**先に潰しておく**）

### 「ソフト側に Postfix を持つ」は成り立たない

各利用者の端末が MTA になる形は、**メールが届かない。**

| | |
|---|---|
| **ポート 25** | 家庭・モバイル回線の ISP は**外向き 25 を塞ぐ**のが普通 |
| **常時起動** | ノート PC は閉じる。**MTA は落ちていると受け取れない** |
| **動的 IP** | 逆引きが合わず、PTR / HELO の整合が取れない |
| **SPF / DKIM / DMARC** | 端末ごとに鍵を配る形になり、**ドメインの評判を端末 1 台が壊せる** |
| **IP reputation** | 家庭用 IP 帯は**最初から拒否される**（Gmail / Outlook） |

**したがって、端末に MTA は置かない。**置くなら**サーバ 1 か所**で、それは中央である。

### 「P2P メール」は、そのままでは届かない

warifu は**両者がオンライン**であることを前提にしている（iroh の直結・D13）。
**メールの本質は store-and-forward** —— 相手が落ちていても受け取れることである。

**オフライン配送には保管所が要る。**保管所は他人の荷物を預かる構造なので、
**`decisions.md` D7（Relay と中継の法的成立性）が未決のまま止まっている。**

---

## 決めたこと（**提案。実装していない**）

**3 段に分ける。段 1 は決定なしで今すぐ進められる。**

### 段 1 — **既存メールのアダプタ**（ドメイン不要・**いま進められる**）

各自が**自分の既存メールアカウント**（Gmail / 社内 IMAP など）を使い、
warifu は**読む口と送る口**を足すだけ。

- **`warifu-read` / `warifu-imap` が既に動いている**（R1〜R5-b・77 件 green・D18〜D23）
- **ドメインも運営も要らない。n=1 で効く**（`PRD §12-5`：「切り分けは『P2P が要るか』で引く」）
- roadmap **Phase 3-b** そのもの。残っているのは**人が資格情報を入れて実際に回す工程だけ**

**これは「フリーメール」ではない。**各自がアカウントを持っている前提である。

### 段 2 — **ドメインを取るが、名簿を持たない**（**§12-3 の条件を満たす形**）

`<公開鍵から導いた文字列>@<ドメイン>` で**受信だけ**を担う。

| | |
|---|---|
| アドレス | **鍵から決まる。**ユーザー名の一意性を調停する中央が要らない |
| 探索 | **できない。**鍵を知らない相手はアドレスを作れない（総当たりは 2^256） |
| 運営がすること | 受け取って、**その鍵の持ち主へ warifu 経由で渡す**だけ |
| **送信はしない** | SPF / DKIM / DMARC と評判の責任が**段違いに重い。**当面は受け取るだけ |

**これでも残る問題**

- **誰でもそのアドレスへ送れる** → **D31（知らない相手は人に取り次がずに断る）と正面から衝突する。**
  原案 §238 は「メールと同じ**誰でも送信でき、受信後に Spam 判定する**構造を避ける」と書いている
- **ドメインが死ぬと全員のアドレスが死ぬ**（中央依存が 1 つ増える）
- **アドレスが人に言えない長さになる**（base32 の公開鍵は 52 文字）。
  言える名前を付けたくなった瞬間、**それが名簿であり、§12-3 に戻る**

### 段 3 — **warifu の中だけのメール**（P2P・**D7 待ち**）

宛先は公開鍵。外のメールとは繋がらない。相手が落ちていても届くように**保管所**を置く。

**D7 が決着するまで着手しない。**他人の荷物を預かる構造だからである。

## 根拠

- **段 1 は新しい決定を要しない。**roadmap にあり、実装が動いており、`PRD §2`（相手がいなくても価値がある）とそろっている
- **段 2 は §12-3 の「探索可能な名簿を持たない」条件を満たしうる**唯一の形である
- **段 3 は D7 に当たる。**順番を入れ替えると、法的整理の前に他人の通信を預かることになる

## 採らなかった案とその理由

| 案 | 採らない理由 |
|---|---|
| **端末に Postfix を置く** | **メールが届かない**（上の 5 点）。届かないものを配ると、原因が利用者側で切り分けられない |
| **ドメイン ＋ 中央 Directory**（企画書 §5 §6 のまま） | **`PRD §12-3` が採らないと決着済み。**Sybil 耐性の根拠が消える |
| **人が選ぶユーザー名を許す** | `taro@domain` へ送れば存在が分かる ＝ **総当たりで探索できる。**§12-3 の条件を満たさない |
| **段 2 で送信もする** | SPF / DKIM / DMARC ＋ IP 評判の運用責任。**1 通の spam でドメイン全体が落ちる** |
| **先に段 3（P2P メール）** | **D7 が未決。**他人の荷物を預かる構造を、法的整理の前に置かない |

## これを止めるべき条件

- **オーナーが `PRD §12-3` を覆す**と決めたとき（**覆せるのはオーナーだけ**・baseline §15）。
  その場合は §12-3 を書き換え、**Sybil 耐性をどう replace するか**を同じ場所に書く
- **段 2 の「誰でも送れる」を D31 とどう両立させるか**が決まらないうちは、段 2 に着手しない
- ドメインの**運営を誰が続けるか**が決まらないとき（**止まると全員のアドレスが死ぬ**）

## 実行状況

**実装していない。**段 1（既存メールのアダプタ）だけは**決定なしで進められる**が、
残っているのは**人が資格情報を入れて実サーバで回す工程**である（`issues/007`・baseline §14）。

## 2026-09-06〜07 —— **入口を「ドメインを持てる人」に絞る**（オーナー決定）

**前提が変わった。**もとの起票は「**不特定多数へフリーメールを配る**」だったが、
オーナーとのやり取りで**入口が定まった。**

> **メアド設定できる個人か、法人が導入できる動線で。**

### なぜこれで `PRD §12-3` とぶつからなくなるか

§12-3 が反対したのは「**運営が 1 つの共通ドメインを持ち、中央 Directory で
username の一意性・公開鍵・routing・復旧・Abuse を担う**」形だった。

**ドメインは利用者（個人または法人）のものにする。**すると ——

| §12-3 の反対理由 | この形では |
|---|---|
| **名簿が探索可能になる** | **全体の名簿が存在しない。**各ドメインの中だけ |
| **運営に Abuse / SPF / DKIM / DMARC の責任** | **運営が居ない。**責任はドメインの持ち主 |
| §0-0 と逆を向く | **中央のサーバ費用を誰も肩代わりしない** |

**Sybil 耐性はむしろ上がる** —— ドメインの取得に実費がかかり、**他人のドメインは名乗れない。**

### 2 つの入口

| | 誰が設定するか | スタッフ / 本人の手間 | 状態 |
|---|---|---|---|
| **個人** | 本人 | アカウント 2 つ・キー 2 つ・確認メール | **敷居あり。半自動化で下げる**（下記） |
| **法人** | **管理者 1 人だけ** | **ゼロ。**warifu を入れるだけ | **こちらが本命** |

**法人のほうが素直である。**ドメインはもともと持っており、払う人が決まっており、
abuse は本人に言え、**社内の名簿はもともと存在する。**

### 事業者の候補（**2026-09-06 に実物で確認**）

**受信**

| | 費用 | 特徴 | 引っかかる所 |
|---|---|---|---|
| **Cloudflare Email Routing** | **無料** | **MX / SPF / DKIM を自動で入れる**。Worker へ渡せる | **DNS を CF に載せる**必要がある |
| **ForwardEmail** | **無料**（ドメイン無制限・受信無制限） | **100% OSS。**監査報告と白書を公開 | **転送のみ。送信は有料** |

**送信**

| | 無償枠 | 引っかかる所 |
|---|---|---|
| **Resend** | **100 通/日・3,000 通/月・ドメイン 3 つ** | ドメイン単位の枠。**人数が増えると足りない** |
| **ForwardEmail** | 無し（**$3/月**で 9,000 通/月） | 有料。**受信と同じ所で完結する** |
| Cloudflare Email Sending | **Workers Paid 限定・Beta** | 無料にならない |
| Amazon SES | ほぼ無料 | **サンドボックス解除の申請が要る** |

**無償枠は変わる。**画面に数字を焼き込まない。

### 半自動化できる範囲（**実物で確認**）

| | 自動化 | 根拠 |
|---|---|---|
| **送信ドメインの登録** | **できる** | Resend の `POST /domains` が**入れるべき SPF / DKIM をそのまま返す** |
| **DNS レコードを書く** | **できる**（CF に載っていれば） | CF の DNS API がある |
| **API キーの取得** | **できない** | **人が事業者の画面で作って貼る**（baseline §14） |
| **転送先の確認** | **できない** | CF が**確認メールを送って人に押させる**。設計上そう |
| Email Routing の有効化 | **未確認** | 公式は画面の手順しか書いていない。**「ある」と決めつけない** |

**人がやるのは 2 回だけ** —— ①キーを 2 つ貼る ②確認メールのリンクを押す。
**「DNS を手で書き写す」が消える。**そこが一番間違える（1 文字違うと**静かに届かなくなる**）。

### 社内では「人が読めるアドレス」を許す

不特定多数向けなら `<鍵の一部>@domain` にして**探索できなくする**必要があった。
**社内は逆で、同僚を名前で引けるべきである。**

**§12-3 が守ろうとしていたのは「知らない他人を探せてしまうこと」**であって、
**同僚を探せるのは、そうあるべき。**社内と社外で規則を変える。

### 新しく要るもの（**個人向けには無かった**）

| | なぜ |
|---|---|
| **退職したら止める** | **失効の口。**`issues/009` の会場鍵の失効と同じ形が要る |
| **配った記録** | 誰にいつ配ったか。**roadmap Phase 6 の Audit の入口** |

### Phase 6 とは分けて考える

`roadmap` **Phase 6**（Organization / Audit / Compliance Archive）は
「**企業向け。Personal が固まってから**」と決まっている（`PRD §8`）。

| | 判断 |
|---|---|
| **試験導入としてスタッフに配る** | **判断不要。**いまの 3 台の延長である |
| **製品として組織向けを作る**（管理画面・ACL・監査・退職時の失効） | **Phase 6 の前倒し。**急がない |

**失効だけは先に要る。**配ったものを止められないのは、配ってはいけない。

### 外との疎通について（**動かない前提を先に潰す**）

**P2P は外との疎通を肩代わりしない。**

- **受信**: MX が指す先が**常時起きている**必要がある → **事業者に任せる**（CF / ForwardEmail）
- **送信**: 家庭・オフィスの IP は**Gmail が最初から拒否する**。**評判は買えない** → **事業者を 1 段通す**

**同じアドレスで、相手が warifu を持っていれば P2P、持っていなければ普通のメール。**
これが成立の形である。
