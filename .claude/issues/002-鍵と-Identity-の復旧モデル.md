## なぜこれを先にやるか

原案には **Device 単位の失効**（§4）はあるが、**全端末を同時に失った場合が書かれていない。**
§15 に `Recovery Key` という語が 1 度出るだけで、モデルが無い。

Local-first（§3.1）で、中央 User Directory も作らない（§21）ということは、
**復旧を頼む相手が構造上どこにもいない。**

**PGP も Keybase も Secure Scuttlebutt も、機能ではなくここで死んでいる。**
先行例が揃って同じ場所で死んでいる以上、これは想定リスクではなく**既知の死因**。

そして **Identity 生成の実装を書き始めた後に決めると、Identity の形自体が変わる。**
だから Phase 1 より前。

---

## 調べる 4 方式

| | 方式 | 先行例 |
|---|---|---|
| a | **復旧しない**（失ったら新 Identity を作り直す） | SSB / 初期の Signal |
| b | **復旧フレーズを人間が保管**（BIP39 相当） | 暗号通貨ウォレット全般 |
| c | **Social Recovery**（信頼する N 人のうち M 人で復旧） | Ethereum 系ウォレット |
| d | **別 Device への事前バックアップ** | Signal / Apple / Google の各種 |

## 各方式について出してほしいこと

**実装方法ではなく、「何を失う方式か」を書く。**

1. **全損時に本当に復旧できるか**（d は「同じ鞄に 2 台」で失敗する。そこまで書く）
2. **復旧できたとき、何が戻って何が戻らないか** — Identity / Device 一覧 / Trust Graph /
   過去メッセージは**別々に決まる**。ひとまとめにしない
3. **なりすましの入口はどこにできるか** — 新しい鍵を旧 Identity に結び付ける経路は、
   **そのまま乗っ取りの経路**。ここが各方式の本当の差
4. **相手側に何が起きるか** — 復旧した本人が「同じ人」だと相手はどうやって知るのか。
   知らせる手段が無ければ、Trust Graph は復旧しても機能しない
5. **一般の人間が実際にできるか** — 紙に書いて保管する / 友人 3 人に頼む が、
   **実際に使う人にできるかどうか**。b は暗号通貨で「できない人が必ず出る」ことが実証済み

### 先行例の死因（**これが本命**）

- **PGP** — 鍵の管理と失効が普及の障害になったと言われるが、**具体的に何が起きたのか**
- **Keybase** — 買収により停止した。**利用者の Identity と Evidence は何が残り何が消えたか**
- **Secure Scuttlebutt** — 鍵の複数端末利用と復旧が構造的にどう詰まったか

3 つとも「機能が足りなかった」のではないことを確認したい。
**違っていたら違うと書いてよい**（上流の前提が間違っていることになる）。

## 調べるときの制約

- **組み合わせを結論にしない。**「b と d を併用すればよい」は誰でも書けるが、
  **既定でどれにするか**が決まらないと実装が書けない。既定を 1 つ選んで理由を書く
- **a（復旧しない）を最初から除外しない。**設計として最も単純で、原則に完全に忠実。
  除外するなら「誰に配れなくなるか」を根拠に除外する
- c（Social Recovery）は Trust Graph と相性が良く見えるが、
  **他人が必要**＝この企画の最初の形（自分の端末 2 台だけ・PRD §2）では成立しない。
  そこを踏まえて評価する
