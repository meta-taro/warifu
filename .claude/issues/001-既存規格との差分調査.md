## これは何のための調査か

**この企画が「新規格」なのか「既存規格のプロファイル」なのかを確定させる。**

原案 §8 は「既に解決されている暗号通信・音声・映像を再発明しない」と書いているが、
**再発明の危険は Transport より Identity と Capability の側に大きい。**
そこは既に何年も揉まれた仕様があり、しかも見た目が自分で書けそうに見えるため、
気づかず自前定義しやすい。

**結論が「既存でおおむね足りる」でも、それは失敗ではない。**
むしろその場合、この企画は新規格ではなく **プロファイル + Reference Implementation** になり、
2 つ目の実装を書く候補が「既存規格を既に実装している人たち」になる。
**ゼロから仲間を探すより桁違いに楽になる。**望ましい結論なので、遠慮なくそう書いてよい。

**この Issue が終わるまで、仕様も実装も書き始めない。**

## 出してほしい形

各項目について、**1 行で判定 + 根拠 URL**。長文の解説は要らない。

```
| 原案の要素 | 既存仕様 | 判定 | 根拠 |
|---|---|---|---|
| Device 単位の鍵と失効 | W3C DID Core | ほぼカバー / 一部不足 / 該当なし | <URL> |
```

判定は次の 3 つだけ。中間の言葉を作らない。

- **ほぼカバー** … そのまま使える。自前定義しない
- **一部不足** … 使うが拡張が要る。**何が足りないかを 1 行で**
- **該当なし** … 既存に無い。**ここだけが「新規格」の中身になる**

### 最後に必ず書くもの（**ここが本題**）

1. **「該当なし」に分類された項目の一覧。**これがこの企画の実質的な新規部分
2. **その一覧が空、または 1〜2 個なら、そう書く。**
   「新規格を名乗る根拠が薄い」という結論を出してよい。**むしろそれが有用な結果**
3. **Keybase が停止したことで、利用者の Trust Evidence がどうなったか。**
   原案 §6 は「外部から Evidence を Import する」設計なので、
   **Evidence の集約点が消えた時に何が起きるかは、この企画の未来そのもの**

## 調べるときの制約

- **原案の設計を擁護する方向に寄せない。**「既存では足りない」という結論のほうが
  仕事が増えて格好がつくが、それは判断を歪める。**足りているなら足りていると書く**
- 仕様の**現在のステータス**（Draft / Recommendation / RFC 番号・最終更新）を必ず添える。
  止まっている仕様に寄せると、そこで一緒に止まる
- **実装の有無**を見る。仕様があっても実装が 1 つも無いなら、
  それは「既に解決されている」ではない
- 分からないものは **分からないと書く**。埋めない
