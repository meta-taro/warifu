## 作るもの

**受信したメッセージを、既定では AI に渡さない読み取り層。**

「本文を要約して token を減らす」ではない。要約するにも AI を呼ぶ。
**呼ばずに済ませるための層**を作る。

## 4 つの仕組み

### 1. Metadata First

既定で本文を返さない。返すのは `from` / `type` / `time` / `priority` / `action_required` だけ。

**本文を返さないことが既定**であり、要求されたときだけ出す。逆にしない。

### 2. Progressive Disclosure

| Level | 出すもの |
|---|---|
| 0 | metadata のみ |
| 1 | 要約 |
| 2 | 構造化した本文 |
| 3 | 原文 |
| 4 | 添付 |

**上げるのは、読み手が要ると判断したときだけ。**
「とりあえず Level 3 で取る」ができてしまうと、この層は無いのと同じになる。

### 3. Deterministic Parser First（**中心**）

**未知の形式に当たったときだけ LLM を呼ぶ。**
そして呼んだその場で **parser rule を作って保存する**。

**一度学習した形式は、二度と LLM を呼ばない。**

- 請求書・予約確認・配送通知・CI の失敗通知は、送信元ごとに形が固定されている
- 同じ形を毎回モデルに読ませているのが、現状の token 消費の主因
- **1 通目だけがコストで、2 通目以降はゼロ**

### 4. Thread Compression / Deduplication

- 過去スレッド全文を毎回渡さない（要約 / 現在の状態 / 未解決の問い / 差分）
- 署名・免責文・ロゴ・引用ブロックを hash で除外する

## Action Inbox

「未読 43 件」ではなく、**今日、人間が判断すること**を上に出す。

```
  承認  3
  支払  2
  返信  1
  処理済 126   ← 開かない
```

warifu には Intent の `kind` が既にある（D14）ので、
これは**新しい通信の仕組みではなく、表示の設計**である。

## 置き場所を間違えない

**Adapter（roadmap Phase 5）の内側に書かない。**

```
   SMTP / IMAP ──┐
                 ├──▶  この層  ──▶  読み手（人 / AI）
   warifu Intent ─┘
```

経路が違っても**同じ層が同じ判断をする**。
Adapter の中に書くと、経路の数だけ同じものを作り直すことになる。

---

## D5 を崩さない

この層は**受信した中身を扱う**ので、D5 の真正面に立つ。

- **parser rule を、受信したメッセージの中身から自動生成して自動適用しない。**
  「この形式はこう読め」と本文に書いておけば parser が乗っ取れる
- **rule は人が見られる形で保存する**（何を抽出しているかが読める）
- **priority / action_required を送信者が自己申告できるようにしない。**
  申告できるなら全員が「緊急」を付ける
- **Level を上げる判断を、送信者側の指示で動かさない**
