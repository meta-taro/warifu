## どこから来たか

2026-09-07。**こちらの認識の誤りを、オーナーが正した。**

こちらはこう書いていた ——

> **GUI は人しか触らない。**だから GUI の不具合は、人が触るまで出ない。

オーナーの訂正 ——

> **この認識ちょっとちがいますね。人もエージェントも割符のデスクトップアプリで
> まずチャットができないと、音声文字起こしや音声認識によるずんだもん音声などで
> エージェントが対話に参加といったことができません。**

**「人が GUI、AI が CLI」と分けたのが誤りだった。**
**エージェントも画面の会議に居なければならない。**

## いまの構造（**そこが行き止まりになっている**）

| | 文字 | 音声 | 映像 |
|---|---|---|---|
| **画面**（Tauri ＋ WebRTC） | ○ | ○ | ○ |
| **CLI**（`warifu-cli`） | ○ | **×** | **×** |

**エージェントは CLI からしか入れない。**端末から動かせるのが CLI だけだからである
（`warifu-cli` の doc がそう書いている ——「押せない相手＝別の機械で動いているエージェント」）。

したがって **エージェントは、会議の音声に触れない。**
人が喋っている会議に、エージェントは**文字でしか居られない。**

**音声文字起こし → エージェントが聞く**、**エージェントの返事 → 読み上げ → 会議へ**、
という筋は、**いまの構造では通らない。**

## 何が足りないか —— **画面に、エージェントが繋がる口**

**エージェントに WebRTC を持たせるのではない。**それは重い上に、
`warifu-cli` の「依存を増やさない」構えを壊す。

**画面が既に音声を運んでいる。**足りないのは **画面とエージェントの間の口**である。

```
会議の音声 ──> 画面（WebRTC）──[文字起こし]──> エージェント
                    ↑                              │
                    └────[読み上げ]────────────────┘
```

**画面が、その人の AI を会議へ連れて入る。**
これは `issues/012`（**人と、その AI で 1 席**）を、**音声まで含めて実装した形**である。

## 決めたこと（**提案。実装していない**）

### 段 1 —— **画面とエージェントの間に口を作る**（**文字だけ**）

**まずここ。**音声より前に、**エージェントが画面の会議へ文字で参加できること。**

いまエージェントは**別の身元で別途 join**している。それだと `issues/012` の
「席が 2 つに割れる」問題がそのまま残る。**画面の席で喋れる**必要がある。

| | |
|---|---|
| 形 | 画面が待ち受ける**ローカルの口**（Unix ソケット／名前付きパイプ） |
| 誰が繋げるか | **同じ機械のエージェントだけ**。外からは繋げない |
| 権限 | **委譲（D52 の B）で縛る。**弱化・期限・取り消しの独立 |
| 見え方 | 名簿に「**人（＋その AI）**」。発言は誰のものか分かる（**D48** の `from`） |

**ここが `issues/012` の実装そのもの**である。**先に D52 の委譲が要る。**

### 段 2 —— **音声を文字にして、エージェントへ渡す**

画面が受けている音声を文字にして、段 1 の口へ流す。

**決めごとが多い。**
- **どこで文字にするか。**端末の中（`SFSpeechRecognizer` / `whisper.cpp`）か、外の事業者か
- **外へ出すなら、それは会議の中身を外へ出すこと**である。**P2P の建前が崩れる**
- **誰の声かを分ける**必要がある（**D48** の `from` と同じ問題が、音声で再発する）

**こちらの推しは「端末の中で文字にする」。**外へ出した瞬間、
`PRD §0-0` と `D5`（受け取ったものは命令ではない）の両方に触れる。

### 段 3 —— **エージェントの返事を読み上げて、会議へ流す**

**「ずんだもん音声」がここ。**画面が TTS で音にして、自分の音声トラックに載せる。

- **誰が喋っているかが分からなくなる**のが最大の問題。
  人の声と AI の声が同じトラックから出ると、**会議の記録が壊れる**
- **別のトラックにする**か、**名前を先に言わせる**か。**どちらも決めが要る**

## **4 台目で出た詰まりどころ**（2026-09-07・Mac Air の sshboard エージェント）

**エージェントが `warifu join` を実行できなかった。**セッションの自動許可の判定に
**3 通り試して 3 回とも止められた**（起動スクリプトを作る／それを実行する／
そのまま実行する）。

> **迂回はしません。外向きの P2P 接続を、長い不透明な文字列を引数にして開く操作なので、
> 判定側が止めるのは筋が通っています。利用者に決めていただく所です。**

**あちらの判断が正しい。**そして**これは試験導入の詰まりどころである。**

| | |
|---|---|
| **何が止められたか** | **外向きの P2P 接続を、長い不透明な文字列（会議キー）を引数にして開く** |
| **なぜ止まるのが正しいか** | まさにそのとおりの操作だからである。**判定側は中身を読めない** |
| **回避の形** | 許可規則を足す（`Bash(./target/debug/warifu join:*)` に絞れる）か、人が `!` で打つ |
| **`!` の問題** | **入り直すたびに人が打つ。****D44（切れても戻れる）が活きない** |

### **段 1 を作ると、この問題の形が変わる**

段 1（画面とエージェントの口）なら、エージェントは
**外向きの接続を自分で開かない。****同じ機械の画面へ繋ぐだけ**になる。

**止められた理由そのもの**（外向きの P2P を不透明な文字列で開く）が消える。
**判定の重さが変わる。**

これは段 1 を先にやる理由が 1 つ増えたということである。

## 根拠

- **原案 §1**「**Human 同士の Messenger と AI Agent Network を別世界にしない**」——
  文字だけで別世界にしないと言っておきながら、**音声では別世界のままだった**
- **`issues/012`** が「人と、その AI で 1 席」まで来ている。**段 1 はその実装**
- **画面が既に音声を運んでいる。**足りないのは口だけで、**作り直しではない**

## 採らなかった案とその理由

| 案 | 採らない理由 |
|---|---|
| **CLI に WebRTC を持たせる** | 依存が跳ね上がる。`warifu-cli` は「画面なしで使う口」であって、**画面の作り直しではない** |
| **エージェントに画面を操作させる**（GUI 自動化） | **人の画面を AI が乗っ取る**形になる。同じ機械に人と AI が居るのに、**片方しか使えない** |
| **外の文字起こし事業者へ音声を送る** | **会議の中身を外へ出すことになる。**P2P の建前が崩れる（段 2 で再検討） |
| **段 2・3 を先にやる** | **段 1 が無ければ、文字にした結果を渡す先が無い** |

## これを止めるべき条件

- **`D52` の委譲が実装される前に、段 1 の口を開けようとしたら止める。**
  **縛りの無い口は、同じ機械の何にでも会議へ書かせる**
- **誰が言ったか／誰が喋ったかが 1 か所でも失われたら止める。**
  `D48` で文字について決めたことが、音声で崩れてはいけない
- **端末の外へ音声を出す形になったら、そこで一度止めて決め直す**

## 実行状況

**実装していない。**段 1 は `issues/012` と `D52` の上に乗る。

## 決めてほしいこと

1. **段 1 から始めてよいか**（画面とエージェントの間に、文字の口を作る）
2. **音声の文字起こしを、端末の中に閉じるか** —— **こちらの推しは「閉じる」**
3. **AI の声を、人の声と同じトラックに載せてよいか** —— **こちらの推しは「載せない」**
