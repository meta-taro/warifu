# roadmap — ai-native-trust-network（叩き）

原案 §22「最初の 90 日」を、**着手可能な量に絞った版**。
オーナーの受領時発言「企画が先行して AI を擁しても生み出すペースが追いつけません」を前提に、
**Month 1〜3 を全部やる形では組まない。**

**位置づけの既定は「単独 OSS の部品」**（PRD §0-c）。
規格として名乗るのは後でよく、後からでも名乗れる。したがって
**仕様書一式（原案 §13 Phase 0）を先に完成させる順にはしない。**

## Step 1 — 差分調査（**最初の実作業・実装より前**）

`issues/001` 1 本だけ。**ここが以降すべての前提。**

DIDComm v2 / W3C DID / VC / UCAN / ZCAP / MLS / Nostr / Matrix / libp2p 系 / Keybase の
どこまでが原案 §4 §6 §9 §3.5 を既にカバーしているかを出す。

**結論が「既存でおおむね足りる」でも失敗ではない。**
その場合この企画は新規格ではなく**プロファイル + Reference Implementation** になり、
2 実装目の候補が既存規格の実装者になる＝ **D1 が一段楽になる**。むしろ良い結果。

**この結果が出るまで、仕様も実装も書き始めない。**
原案 §8「再発明しない」を Transport だけでなく Identity と Capability にも適用する。

## Step 2 — 復旧モデルの決着（`issues/002`）

D2。全端末を失った人間の Identity をどうするか。
**Phase 1（Identity 生成）を書き始める前に決める。**後から入れると Identity の形が変わる。

調査は「どう実装するか」ではなく「**何を失う方式か**」を出す形にする。

## Step 3 — n=2 プロトタイプ（**他人を 1 人も登場させない**・`issues/003`）

PRD §2。**自分の PC の Agent ⇄ 自分のスマホの Agent** が、
どのクラウドアカウントも作らずに Identity を確立してつながる形。

原案 §22 Month 2 の CLI Identity / Device Key / QR Connection / Local Trust Graph /
E2EE Text / Revoke が、**この 1 つの用途で全部必要になる。**

**部品として立てる以上、これが最初に世に出るもの。**
仕様書より先にこれを出す（規格を名乗るなら順序は逆だが、いまは名乗らない）。

**ここまでで一旦止めて評価する。**

## 期限を置かない理由

原案 §22 は 90 日で区切っているが、**この叩きでは日付を置かない。**

普及速度は予測できない。
Chrome がシェアを取るまで 12 年かかった（Android という別要因を使ってもなお）例のとおり、
**「良いものだから早く普及する」という前提でスケジュールを引くと、
遅れているのか正常なのかが判定できなくなる。**

**部品として立てる限り、これは問題にならない。**使うのがまず自分たちだから、
普及が遅くても価値が減らない（PRD §0-c）。
判定基準（D1）が要るのは、**規格を名乗った後だけ**。
