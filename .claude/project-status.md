## 2026-09-04（追補 8）— **落ちたのに終わっていなかった**（`warifu host`）

前のセッションが急に落ちた。その跡を読んだら、**主催のプロセスが残っていた。**

なお、再起動で**開発環境も 1 つ壊れていた**。`nodebrew` の現行が
**v22.23.2（arm64）から v24.11.1（x86_64）へ切り替わっており**、画面のテストが
`Cannot find module @rollup/rollup-darwin-x64` で全滅していた（この機械は Apple M1）。
`nodebrew use v22.23.2` で戻し、**画面 101 件 green** を実測した。

```
$ ps -o pid,stat,etime -p 63908
  PID STAT ELAPSED
63908 S    54:52
```

ログの最後は 17:03 の
`warifu: 経路で落ちました: 送り終わる途中で落ちました: connection lost`。
**誤りを出したのに、55 分そのまま生きていた。**UDP は 1 本も掴んでおらず、
スレッドは 2 本、CPU は 0.0%。**ランタイムは畳み終わっていて、出口で止まっていた。**

標準入力へ 1 行流し込んだら、その場で終わった。**原因はこれである。**

### 何が起きていたか

`tokio::io::stdin` は専用のブロッキングスレッドで `read(2)` を呼ぶ。
`#[tokio::main]` はランタイムを畳むときに**ブロッキング処理の完了を待つ**。
`warifu host < パイプ` のように**標準入力が開いたまま**だと read は返らない。
**相手が落ちても、プロセスが終わらない。**

人から見ると「落ちたのに終わっていない」。**次の待ち受けを建てたつもりが二重になる。**

### 直し方

`#[tokio::main]` をやめ、ランタイムを自分で持って `shutdown_timeout(ZERO)` で畳む。
**止まったままの read を待たない。**

### 実測

| | 直す前 | 直した後 |
|---|---|---|
| 単体テスト（止まった read を置く） | **10.005 秒待たされた** | **0.00 秒** |
| 実物（相手を `kill -9`） | **終わらない**（55 分の実績） | **33 秒で終わった** |

33 秒は QUIC が相手の消失に気づくまでの時間で、**気づいた後は即座に終わっている。**

### ついでに分けた — **「帰った」と「落ちた」が同じ文言だった**

主催の手元には、どちらでも `経路で落ちました: …` が出ていた。
**人はこの 2 つで次の手が変わる**（帰ったなら会議は終わり、落ちたなら鍵を作り直す）。

`warifu_net::Error::Closed` を足して分けた（`FinishedEarly(0)` は閉じた・途中で切れたのは落ちた）。

```
（挨拶して帰った相手）  warifu: 相手が帰りました
（kill -9 で消えた相手）warifu: 相手が落ちました（経路で落ちました: 受け取る途中で落ちました: connection lost）
                        warifu: この会議キーはもう使えません。入り直すには新しい鍵が要ります
```

**落ちた相手には締め（`finish`）に行かない。**そこで出る誤りが、落ちた理由を覆い隠していた。

### 画面（Tauri）も同じ穴だった

`warifu://closed` は**どちらでも同じ**を出していた（`link.closed`「経路が閉じました。」）。
CLI だけ直しても、**人が見るのは画面の方**である。

Rust 側で訳（`left` / `lost`）を載せ、画面が文言を選ぶようにした。
`link.lost` を 4 言語に足し、**`CRITICAL_KEYS` に入れた**（誤訳すると人の行動が変わるため）。

```
（帰った）warifu: 相手が退出しました。
（落ちた）warifu: 相手との経路が切れました。この会議キーではもう入室できません。
                  新しい会議キーを作り直してください。
```

翻訳者への注記も付けた ——「**再接続しています**」「**復旧を試みています**」と読める訳にしない。
待てば戻ると誤解すると、**人は待ち続ける。**

### 画面で実物を出して確かめた（**この機械で・18:20**）

`.app` を差し替えて開き直し、**画面で会議を建て、CLI で入り、`kill -9` した。**

```
（32 秒後）
帯          相手との経路が切れました。この会議キーではもう入室できません。
            新しい会議キーを作り直してください。
チャット欄  PH25ZNBAIMC2… との経路が切れました
ログ        経路が終わった: PH25ZNBAIMC2…（lost）
```

### 画面を見て、さらに 2 件出た

**① 名簿だけ「退室しました」のままだった。**帯は「経路が切れました」なのに、
同じ相手がチャット欄では**退室**になっていた。`片付ける()` が
`EVENT_LEFT`（本人が抜けた）と `EVENT_CLOSED`（経路が終わった）の両方から
呼ばれていて、**どちらでも `chat.left` を書いていた。**

`出来事` に `切断` を足し、`chat.lost` を 4 言語に入れた。
**退室は本人の意思、切断は事故である。**

**実際に通した**（この機械の中で 2 つ動かして）。

```
$ warifu host --idle 8          → 会議キーが標準出力へ
$ echo "こんにちは" | warifu join '<会議キー>' --idle 5
→ host 側の標準出力に「こんにちは」が出る
```

割符で相手を確定し、戸口を通り、会議として受け取られている。

### 18. **待っているはずが、勝手に諦めていた**

会議キーを出して待っていたら、繋がる前に落ちた。

```

```

**`--idle` は「繋がった後に何も来ない時間」にしか効いていなかった。**
**繋がる前の待ち時間**は下の層（iroh）の既定に任せており、そこで先に落ちていた。

**「待っています」と言った以上、こちらの都合で勝手に諦めてはいけない。**
来るまで待ち直し、**会議キーが切れたときだけ諦める**ようにした。

あわせて `--ttl <秒>` を足した。既定の 10 分では、
**相手が建てている間に切れる**（実際に切れた）。

## 既知の問題

| | 内容 |
|---|---|
| **UCAN を読む前に `warifu-capability` を書いた** | `issues/001` が「自前設計する前に必ず読む」と名指しで警告していた所を踏んだ。**UCAN 1.0 が上位互換**（委譲の連鎖まである）。寄せるかは上流の判断（依存ゼロ＝ D18 / D24 を崩すため） |
| **定員は文献値のまま** | 既定 **12** / 外枠 16（D27）。**どちらも手元の回線で実測していない。**12 人 720p で上下 16.5 Mbps。M6 で確かめる（`issues/005`） |
| **回線を実際に測っていない** | `warifu-link` は数値を入れれば答えを出す所まで。**流れた量も空き帯域の見積もりも、出すのは経路側（WebRTC の統計）で M5 以降**（D28 / D29） |
| **D7 が未決** | **中継（SFU / Cooperative Relay）に進めない。**人数の問題ではない（D27 で訂正）。法的整理が要る |
| **D2 が未決** | 全端末を同時に失った場合の復旧方式。実装は止まらないが、**配布前には決着が要る** |
| **中継を使っていない** | M2 は直接つながる経路しか持たない。**対称 NAT・厳しい社内網では繋がらない。**中継が要ると分かった時点で、自前 Relay かどうかを D3 と一緒に決める（D13） |
| **2 台どうしまで** | 3〜4 人の網（mesh）はまだ無い。帯域と CPU は M6 で実測する |
| **3 人目の住所をどう知るか未決** | 名簿が運ぶのは公開鍵だけで、経路の当てが入っていない。**M6 で決める**（M4 を大きくしないため先送りした・D15） |
| **送信元は詐称できる** | 規則は送信元で当たる。IMAP の `From` は誰でも書ける＝**詐称した相手には、その規則で読まれる**。今これが致命傷にならないのは**規則が抽出しかできない**から。**規則に実行を足すなら、署名の検証を先に**（D19 / PRD §12-2） |

| **荷物の切れ目を二重に持たない** | Intent 側には荷物の長さを書いていない。**途中で切れたことはこの層では分からない**（下の経路が落とす）。これは D14 で意図して選んだ |
