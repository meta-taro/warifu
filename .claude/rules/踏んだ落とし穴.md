## 1. シェルの変数名は ASCII だけ

コメントも、文字列も、日本語で書いてよい。**変数名だけは書けない。**

```bash
前=$(git describe ...)     # → 前=v0.1.0-alpha.15: command not found
prev=$(git describe ...)   # ○
```

**2026-09-10 に 2 度、2026-09-13 に 3 度目を踏んだ。**
1 度目は commit の本文を組むところ、2 度目は `release.yml` の中、
3 度目は**見張りのスクリプト**である（`いま=13: command not found`）。

**3 度目がいちばん悪かった** —— スクリプトは動いているように見え、
**「Issue に動きが無い」と読めてしまった。**壊れ方が「黙って動かない」なので気づけない。

`.rs` / `.ts` の識別子は日本語で書ける（そう書いている）。**シェルだけが違う。**

### 同じ日に踏んだ親戚

**空白は、どの言語でも識別子に入れられない。**

```rust
fn 見比べる(場所: &Path, 画面の版: &str, cli の出力: &str)   // ← 空白。通らない
```

```ts
const WINDOWS の直し方 = [...]   // ← 空白。通らない
```

**日本語で書けることと、空白が入れられることは別である。**
**Rust の関数名は数字で始められない**（`fn 0_を言えば…` も落ちた）。

## 6. **静的な棚を測る試験は、錠を持たせる**（並んで走ると混ざる）

Rust の試験は**既定で並んで走る。**`static Mutex<Vec<…>>` のような
**プロセスに 1 つしか無い棚**を、複数の試験が触ると**互いの値を見る。**

```rust
#[test]
fn 発言でない行は控えない() {
    let 前 = 直近の発言.lock()….len();   // ← ここで 0
    控える(&FromDesk::Joined { … });      //    隣の試験が 200 本積んだ
    assert_eq!(…len(), 前);              // ← left: 200 / right: 0
}
```

**2026-09-17 に踏んだ。**壊れ方が悪い —— **`控える` は正しく動いている。
落ちたのは測る側が並んでいたからで、失敗の文面は実装のバグに見える。**

**錠を 1 本置いて、棚を空にしてから測る。**

```rust
static 発言の順番: Mutex<()> = Mutex::new(());

fn 発言も一つずつ() -> std::sync::MutexGuard<'static, ()> {
    let 番 = 発言の順番.lock().unwrap_or_else(std::sync::PoisonError::into_inner);
    直近の発言.lock().unwrap_or_else(std::sync::PoisonError::into_inner).clear();
    番
}
```

**棚ごとに別の錠にする**（同じ錠にすると、関係の無い試験どうしが待ち合う）。
**毒された錠は `into_inner` で受ける** —— 先に落ちた試験のせいで、後続が
「錠が毒されている」で全部落ちるのを防ぐ（失敗が 1 本のとき 1 本だけ落ちてほしい）。

### 同じ根の親戚（**2026-09-16**）

**固定した socket のパスも、プロセスに 1 つしか無いもの**である。

## 8. **記録を数える前に、走りで切る**（追記なので古い失敗が「いま」に見える）

### 切り方

**走りの頭は、必ずこの行である。**

```
[warifu +0.000s] 起動しました。ここから経路の要所を書き出します（+秒 は起動からの経過）
```

**`+秒` は起動からの経過**なので、**数字が小さくなった所が新しい走りの頭**である。

```bash
# いちばん新しい走りだけを見る
awk '/起動しました。ここから経路の要所/{buf=""} {buf=buf $0 "\n"} END{printf "%s", buf}' warifu.log
```

**「全体で N 件、うちこの走りで M 件」と書く。**
**M だけ書くと、読む側が全体と比べられない。**
**N だけ書くと、直ったものを直っていないことにする。**

**これは AI 側が何度もやっている間違いである**（症状が出た所と原因が在る所の取り違えと同じ根）。

## 11. **試験の入力を自分で作ると、実物に無い項目を探していても通る**

**2026-09-18、Mac Air の実測から出た。**

```
実測   送り 映像 0 / 音 0（音の積もり **不明**）
```

**本数は 0 になったのに、積もりが「不明」のままだった。**
**版の問題だと思ったが、違った** —— **在らないものを探していた。**

W3C webrtc-stats ——

```
totalAudioEnergy    inbound-rtp     **在る**
totalAudioEnergy    outbound-rtp    **無い**
                    → 「For audio levels of tracks attached locally,
                        see **RTCAudioSourceStats** instead」
                    → RTCAudioSourceStats の型名は **media-source**
```

**送っている側の音量は、送っている行には載っていない。**
**だから送り側の積もりは、どの版でも永久に「不明」だった。**

### **試験は 4 本とも通っていた**

```ts
const 音 = (向き, 本数, 積もり?) => ({
  type: 向き, kind: 'audio', packetsSent: 本数,
  totalAudioEnergy: 積もり,          // ← **自分で outbound-rtp に載せた**
});
送り受けを言い表す([音('outbound-rtp', 121, 0)]);   // → 「無音」。**通る**
```

## 12. **`gh` が落ち続けるのに `curl` は通る**（同じホスト名の、別 IP）

**2026-09-22〜23 に何度も踏んだ。**`gh` が同じ所で落ち、**同じ瞬間に `curl` と `nc` は通る。**

```

curl https://api.github.com → **200**（同じ宛先）
nc -z 20.27.177.116 443     → **通る**
```

**回線でもクライアントでもない。**——**その瞬間にどの IP を引いたか**である。

### 見分け方（**失敗は必ず 4.01 秒**）

```bash
for i in 1 2 3; do curl -s -o /dev/null -w "%{http_code} %{time_total}s ip=%{remote_ip}\n" --max-time 10 https://github.com/; done
#   000  **4.016s**  ip=          ← **接続タイムアウト**（外れ IP）
#   200  2.131s  ip=20.27.177.113 ← 当たり
#   200  1.124s  ip=20.27.177.113
```

**成功は 0.1〜2 秒、失敗はきっかり 4.01 秒。**
**「重い」ではなく「繋がっていない」**なので、待っても変わらない。

```bash
dscacheutil -q host -a name github.com   # **いまどの IP を引いているか**
```

### なぜ `gh` だけが落ち続けるのか

**`gh` は掴んだ接続（外れ IP）を使い続け、`curl` / `nc` は都度引き直して当たりを踏む。**
**だから `gh` の再試行は効かない**（同じ外れを掴み直す）。

### 手

```
1. **`gh` が落ちたら、まず引いている IP を見る**（`dscacheutil`）
2. 外れなら**数十秒待って引き直す。**`gh` の連打は効かない
3. 急ぐなら **`curl` に逃げる** ——
   `gh api …` の代わりに `curl -H "Authorization: Bearer $(gh auth token)"`。
   **`--retry 6 --retry-all-errors` を付ける**（1 回目が外れでも 2 回目で当たる）
```

**2026-09-22 に、この形で成果物を落とした**（`gh release download` が 8 回だめ →
`curl` ＋ `--retry` で 2 ファイルとも一致確認まで通った）。

### **訂正**（2026-09-24）——**IP だけでは説明できない**

**上の「どの IP を引いたか」は、原因の全部ではなかった。**

```

         **既定の経路が 2 本**あり、口を指定しないと落ちた
         en0（有線）で api.github.com が **5 回連続 4.01 秒**
         en1（Wi-Fi）で同じ宛先が **0.175 秒で 200**
```

**私はそれを見て「有線から外へ出られない」と書いた。強すぎた。**

```

  1 回目 失敗 4.01s ／ 2 回目 失敗 4.01s ／ **3 回目 200**
  git ls-remote  1〜3 回目だめ → **4 回目で通る**
```

**引いている IP が 1 件で、それが通る IP でも、繋ぎ始めの 2〜3 回に 1 回しか通らない。**
**つまり「外れ IP を掴む」だけでは説明できない。**

**そして GitHub の話でもなかった。**同じ機械から**外向き全部**が落ちていた。

**「どの IP を引いたか」も「GitHub が」も外れ。**——**この機械の外向き TCP が、3〜4 回に 1 回しか張れない。**
**ほかの機械（ASUS）は 1 回で通る。**関門へは 0.47 ms で届き、名前も引ける。**張る所だけが落ちる。**

**原因は分からない。**オーナー（2026-09-24）——

> **理由は不明だけど、しゃーない。通るときは通るので、通るまでやるしかない。**

### 手（**分からないままの運用**）

```

**こちらが呼ぶものは、最初から再試行を付ける**（curl の --retry 6 --retry-all-errors）
```
