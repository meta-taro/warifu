## 1. シェルの変数名は ASCII だけ

コメントも、文字列も、日本語で書いてよい。**変数名だけは書けない。**

```bash
前=$(git describe ...)     # → 前=v0.1.0-alpha.15: command not found
prev=$(git describe ...)   # ○
```

**2026-09-10 に 2 度、2026-09-13 に 3 度目を踏んだ。**
1 度目は commit の本文を組むところ、2 度目は `release.yml` の中、
3 度目は**見張りのスクリプト**である（`いま=13: command not found`）。

**3 度目がいちばん悪かった** —— スクリプトは動いているように見え、
**「Issue に動きが無い」と読めてしまった。**壊れ方が「黙って動かない」なので気づけない。

`.rs` / `.ts` の識別子は日本語で書ける（そう書いている）。**シェルだけが違う。**

### 同じ日に踏んだ親戚

**空白は、どの言語でも識別子に入れられない。**

```rust
fn 見比べる(場所: &Path, 画面の版: &str, cli の出力: &str)   // ← 空白。通らない
```

```ts
const WINDOWS の直し方 = [...]   // ← 空白。通らない
```

**日本語で書けることと、空白が入れられることは別である。**
**Rust の関数名は数字で始められない**（`fn 0_を言えば…` も落ちた）。

### `gh issue comment --body` も同じ

**2026-09-15 に踏んだ。**`--body "… `記録の版 2` が出ない …"` と書いて、
**バッククォートの中が実行され、その部分が投稿から消えた。**

```
(eval):3: command not found: 記録の版
```

**投稿は成功してしまう**（欠けたまま）。**気づくのは相手が読んだ後**である。
**`--body-file` と heredoc で渡す。**

```bash
cat > /tmp/c.md <<'MD'
… `記録の版 2` …
MD
gh issue comment 19 --body-file /tmp/c.md
```

### Rust のモジュール名は**ファイル名になる**ので ASCII だけ

```rust
mod 候補;   // → error[E0754]: trying to load file for module `候補`
mod pick;   // ○（ファイルは pick.rs）
```

**2026-09-16 に踏んだ。**`.rs` の**中の識別子**は日本語で書けるが、
**モジュール名はファイル名に写る**ので書けない。

### 空白は、この日も踏んだ

**2026-09-16、4 度目。**`fn 重なったものは_1 つにする()` ——
**`_1` のあとに全角空白**が入っていた。

```
error: missing parameters for function definition
   fn 重なったものは_1 つにする() {
                       ^
```

**数字のあとに区切りを入れたくなると、空白を打つ。**そこが癖である。

### commit message も同じ

```bash
git commit -m "… `apps/desktop/…/+page.svelte` は …"   # ← バッククォートが走る
#   → command not found: +page.svelte（メッセージの一部が消える）
git commit -F - <<'MSG' …                               # ○ heredoc で渡す
```

## 2. Python を CI で回すなら、**読む所と出す所の両方**に文字コードを書く

日本語を扱うスクリプトを Windows の CI で回すと、**2 か所で落ちる。**

```python
# 読む —— text=True だけでは、その機械の既定（Windows は cp1252）で読む
subprocess.run([...], encoding="utf-8", errors="replace")

# 出す —— 標準出力も cp1252 なので、print で落ちる
for 口 in (sys.stdout, sys.stderr):
    if hasattr(口, "reconfigure"):
        口.reconfigure(encoding="utf-8", errors="replace")
```

**2026-09-10 に、この 2 つを別々のタグで踏んだ**（alpha.17 で読む所、alpha.18 で出す所）。
**片方だけ直して「直った」と思った**のが間抜けだった。

**手元で確かめられる。**

```bash
PYTHONIOENCODING=cp1252 python3 scripts/<名前>.py
```

**タグを打つ前にこれを回す。**CI で 1 往復するより速い。

## 5. `cp` で実行ファイルを上書きしない

macOS は**そのパスの署名を覚えている**ので、中身だけ差し替えると
**`Killed: 9`（SIGKILL）**になる。**消してから置く。**

```bash
rm -f ~/.local/bin/warifu && cp <新しいもの> ~/.local/bin/warifu   # ○
```

2026-09-13 に踏んだ。**エラーは出ず、ただ黙って死ぬ**ので原因が分かりにくい。

## 6. **静的な棚を測る試験は、錠を持たせる**（並んで走ると混ざる）

Rust の試験は**既定で並んで走る。**`static Mutex<Vec<…>>` のような
**プロセスに 1 つしか無い棚**を、複数の試験が触ると**互いの値を見る。**

```rust
#[test]
fn 発言でない行は控えない() {
    let 前 = 直近の発言.lock()….len();   // ← ここで 0
    控える(&FromDesk::Joined { … });      //    隣の試験が 200 本積んだ
    assert_eq!(…len(), 前);              // ← left: 200 / right: 0
}
```

**2026-09-17 に踏んだ。**壊れ方が悪い —— **`控える` は正しく動いている。
落ちたのは測る側が並んでいたからで、失敗の文面は実装のバグに見える。**

**錠を 1 本置いて、棚を空にしてから測る。**

```rust
static 発言の順番: Mutex<()> = Mutex::new(());

fn 発言も一つずつ() -> std::sync::MutexGuard<'static, ()> {
    let 番 = 発言の順番.lock().unwrap_or_else(std::sync::PoisonError::into_inner);
    直近の発言.lock().unwrap_or_else(std::sync::PoisonError::into_inner).clear();
    番
}
```

**棚ごとに別の錠にする**（同じ錠にすると、関係の無い試験どうしが待ち合う）。
**毒された錠は `into_inner` で受ける** —— 先に落ちた試験のせいで、後続が
「錠が毒されている」で全部落ちるのを防ぐ（失敗が 1 本のとき 1 本だけ落ちてほしい）。

### 同じ根の親戚（**2026-09-16**）

**固定した socket のパスも、プロセスに 1 つしか無いもの**である。
`cargo test` を 2 本同時に回すと `AddrInUse` で落ちた ——
**`std::process::id()` をパスに混ぜて避けた。**

**確かめ方は同じ。「3 回同時に回して 3 回通る」まで見る。**

```bash
for n in 1 2 3; do cargo test --lib 2>&1 | tail -3 & done; wait
```

**1 回通っただけでは、直った証拠にならない**（並びの運で通る）。

## 7. **画面が埋まっているかは、`.app` の中のファイルを数えても分からない**

`src-tauri` で `cargo build --release` すると、**画面の入っていない
「dev 版」の実行ファイルが建つ**（起動すると `localhost:1420` を見に行って、白い窓が出る）。
**`pnpm tauri build` を使う。**

**そこまでは合っている。問題は検め方である。**

```bash
# ✗ **これは良い束でも 0 になる**
find warifu.app -path "*_app/immutable*" -type f | wc -l
#   → 0（**画面は実行ファイルの中に埋まっているので、束にファイルとして出ない**）

# ○ 実行ファイルの中の、資材の名前を数える
strings -a warifu.app/Contents/MacOS/warifu-desktop | grep -c "_app/immutable"
#   → 20（埋まっている）
```

**2026-09-17 に、自分で決めた検め方に自分で引っかかった。**
`find` が 0 を返したので「dev 版を配ってしまった」と思ったが、
**正しく建った束だった**（`Contents/Resources` には `icon.icns` しか無いのが正常）。

**画面の文言を `strings` で探すのは、別の理由で駄目である** ——
**資材は Brotli で圧められている**ので、文言は平文で入っていない。
**探せるのは「資材の名前（`_app/immutable/...`）」だけ**で、そこは圧まっていない。

| 見るもの | `find` で数える | `strings` で数える |
|---|---|---|
| 資材の名前（`_app/immutable/…`） | **0。使えない** | **使える** |
| 画面の文言（「ルームに入る」など） | 0 | **0。圧まっているので使えない** |

**検め方そのものが嘘をつくと、良い物を捨てることになる。**
