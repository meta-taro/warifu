## D1. 2 つ目の実装を誰が書くのか（**未決・最優先**）

**状態**: 未決 / **決着期限**: Phase 0 の仕様公開より前 / **決めるのは**: オーナー

### 何が問題か

原案 §19 は Multiple Implementations と Vendor-neutral Governance を掲げているが、
**§20 の成功条件 8 項目はすべて自社実装だけで ✓ が付く。**
8 個全部達成しても、規格として成立したかは 1 ミリも分からない。

規格は機能不足で死ぬのではなく、**2 実装目が現れずに死ぬ**。
1 実装しかない間、仕様書は「実装の説明文」であり、
**仕様の穴は自社実装同士では原理的に見つからない**（同じ誤読を両側が共有するため）。

### 選択肢

| | 方針 | 内容 | 効いてくる所 |
|---|---|---|---|
| **A** | **既存規格に寄せる** | `issues/001` の結果 DIDComm v2 + UCAN で足りるなら、**新規格を名乗らずプロファイルにする**。2 実装目の候補が既存規格の実装者になる | S1〜S3 の難度が一段下がる。**最も現実的** |
| **B** | 新規格として立て、2 実装目を待つ | 原案どおり。ただし**待つ相手が誰か・いつまで待つかを書かない限り、待っていない状態と区別できない** | 期限と判定基準が要る |
| **C** | 規格を名乗らない | OSS 製品として出し、§19 のガバナンス原則を取り下げる | 失敗ではない。**名乗りと実態を一致させるだけ** |

### 決めておくこと（どの選択肢でも）

- **判定期限**（例: 仕様公開から N か月で S1〜S3 が 0 件なら C へ移行する）
- **その時点で何をするか**（名乗りを変える / 続ける / 畳む）

**AI 側から推奨は出さない。**普及速度の予測は、こちらの訓練データが
「12 年かかった側の平均」でできている以上、**AI の同意も反対も証拠にならない**
（2026-08-15 オーナー指摘）。
出せるのは「判定基準が無い状態は判定不能である」という構造の指摘だけ。

## D2. 全端末を失った人間の Identity（**未決・Phase 1 より前**）

**状態**: 未決 / **決着期限**: Phase 1 着手前 / **決めるのは**: オーナー（方針）＋このリポジトリ（実装比較）

### 何が問題か

原案 §15 に `Recovery Key` の語が 1 度出るだけで、モデルが無い。
§4 の Device 失効は**残存端末が 1 台でもあれば**成立するが、全損時は主体がいない。
Local-first（§3.1）＋中央 Directory を作らない（§21）＝**復旧を頼む相手が構造上いない。**

**PGP / Keybase / Secure Scuttlebutt は、機能ではなくここで死んだ。**
想定リスクではなく**既知の死因**として扱う。

### 選択肢

| | 方式 | 得るもの | 失うもの |
|---|---|---|---|
| **a** | **復旧しない**（鍵を失ったら新 Identity） | 設計が最も単純・原則に完全に忠実 | **一般の人間に配れない。**Trust Graph も履歴も消える |
| **b** | 復旧フレーズ（BIP39 相当）を人間が保管 | 追加の主体が要らない | **紙を失う人が必ず出る**。暗号通貨で実証済み |
| **c** | Social Recovery（信頼する N 人の M 人で復旧） | Trust Graph をそのまま使える＝**この企画と最も相性が良い** | **他人が必要**＝ n=1 では成立しない（PRD §2 と衝突） |
| **d** | 別 Device への事前バックアップ | §2 の「自分の 2 台」と一致 | **全損に効かない**（同じ家・同じ鞄で消える） |
| **e** | **探索できない復旧アンカー**（復旧だけを担い、名簿を持たない中央） | **全損に効き、他人も紙も要らない**＝一般の人間に配れる | **中央が 1 つ増える**（§0-0 と正面から擦れる）・アンカー自身が攻撃対象になる |

**組み合わせが前提**（b + d を既定、c を任意、a は明示的に選べる形）。
**ただし「組み合わせにする」は決定ではない。**どれを既定にするかを決める。

### 併せて決めること

- 復旧で**戻るもの / 戻らないもの**（Identity・Device・Trust Graph・過去メッセージは別々に決まる）
- 復旧できたことを**相手にどう伝えるか**（新鍵を旧 Identity と結び付ける経路＝**なりすましの入口**）

### 2026-08-17 追記 — **決着を待たずに Identity を書ける形にする**（D9 / D10 に伴う）

roadmap Step 2 は「D2 を決めるまで Phase 1（Identity 生成）を書き始めない」としていた。
理由は**後から入れると Identity の形が変わる**から。**この理由は正しいが、回避できる。**

**鍵を乱数から直接作らず、1 本のシードから決定論的に導出する形にしておけば、
a〜d のどれを既定に選んでも Identity の形が変わらない。**

```
  シード（32 byte）
    ├─ Profile 鍵（Personal / Work …）
    │    ├─ Device 鍵（PC）
    │    └─ Device 鍵（スマホ）
    └─ …
```

| D2 の選択肢 | シード導出と両立するか |
|---|---|
| **a** 復旧しない | する（シードを捨てるだけ） |
| **b** 復旧フレーズ | する（**シードをそのまま語句にする**のが BIP39） |
| **c** Social Recovery | する（分割の対象がシードになる） |
| **d** 別 Device へ事前バックアップ | する（複製の対象がシードになる） |
| **e** 探索できない復旧アンカー | する（預ける対象がシード、またはその分割片になる） |

**4 つすべてと両立する。**したがって「どれを既定にするか」は後で決めてよく、
**D2 は Identity 実装のブロッカーではなくなる。**

**ただし D2 が消えたわけではない。**「どれを既定にするか」「復旧で何が戻り何が戻らないか」
「復旧を相手にどう伝えるか（なりすましの入口）」は**未決のまま**であり、
**人に配る段階までに決める必要がある**（`issues/003` の実機検証より前）。

- **これを止めるべき条件**: 選択肢 c（Social Recovery）を既定にすると決めた場合。
  c は「他人が必要」なので PRD §2（n=1 で価値が出る）と衝突し、
  **シード導出とは別の論点として再検討が要る**

### 2026-09-01 追記 — **選択肢 e（探索できない復旧アンカー）**

別件で受領した企画書（P2P Agent Mail / 全 56 章・PRD §12）が、
**共通ドメイン ＋ 中央 Directory** を前提に置いていた。そこでは Directory が
username の一意性・公開鍵配布・routing・**アカウント復旧**・Abuse 対策をまとめて担う。

**この形は「巨大中央 User Directory を作らない」と真逆なので採らない**（PRD §12-3）。
だが**採らないことと、そこから何も学ばないことは別**である。
企画書が持ち込んだのは新しい問いではなく、**D2 への答えの 1 つ**だった。

**要点は「中央を置くか」ではなく、「その中央が探索可能な名簿を持つか」。**

「巨大中央 User Directory を作らない」を Sybil 耐性の根拠として使えるのは、
**探せない相手には大量になりすます意味が無い**からである。
逆に言えば、**探索可能性さえ与えなければ、中央があっても Sybil 耐性は落ちない。**

| 中央が持つもの | Sybil 耐性への影響 |
|---|---|
| **名簿**（username → 鍵 / 所在を第三者が引ける） | **落ちる。**なりすます相手を探せる＝偽 Identity に価値が生まれる |
| **復旧アンカー**（本人しか引けない・他人を探せない） | **落ちない。**引くには本人の持ち物が要り、他人の存在は観測できない |

選択肢 e は後者だけを担う中央である。a〜d のどれとも軸が違う
（a は捨てる / b は紙 / c は他人 / d は自分の別端末 / **e は他人でも紙でもない預け先**）。

**未決のまま残すこと**（e を採る場合に決める必要がある）:

- **§0-0 との折り合い。**思想は「中央のサーバー費用を誰かが払う構造を置き換える」であって
  「中央が 1 つも無い」ではない。だが**復旧アンカーが落ちたら誰も復旧できない**なら、
  結局そこを誰かが買い続けることになる。**アンカー自体を参加者が分担して持てるか**が分かれ目
- **アンカーは何を預かるか。**シードそのものを預ければアンカーが本人になれる。
  分割片なら成立するが、**残りの片をどこに置くか**で b / c / d に戻る
- **本人であることをアンカーにどう示すか。**全端末を失った人間には示すものが無い、
  というのが D2 の出発点なので、**ここで循環しないか**を最初に確かめる
- **アンカーが名簿を持っていないことを、利用者はどう検証するか**（「持たない」と宣言するだけなら
  中央 Directory と区別が付かない）

**この追記は e を採用する決定ではない。**a〜d と並ぶ選択肢として起こした、というだけである。

## D3. Relay を自社運用したときの法的位置づけ（**未決・調査はこのリポジトリ**）

**状態**: 未決 / **調査**: `issues/004` / **決めるのは**: オーナー（運用可否）

原案 §3.2 が Relay を許容した時点で、日本では次が発生する。

- **電気通信事業法**上の位置づけ（届出の要否。他人の通信を媒介する）
- **通信の秘密**（E2EE で中身が読めなくても、**誰と誰がいつ通信したかは持つ**）
- 保存・開示要求（**何を持っていないか**を設計で言い切れるか）

**E2EE は上記のどれも免除しない。**

### 叩きとしての暫定方針（覆してよい）

- **仕様側は Relay を許容したまま**（設計としては妥当なので変えない）
- **自社での Relay 運用は Phase 2 まで行わない**
- 検証は「自分の端末間」＋「自分で立てたローカル Relay」に限定する
- **Relay が持つメタデータの最小化を、法務判断より先に設計で決める**
  （持っていなければ、要求されても出せないし、漏れない）

## D4. ライセンス — Spec と実装を分ける（**叩きとして確定・覆せる**）

**状態**: 叩きで確定 / 原案 §18 は 1 つ選ぶ前提だが**分ける**

| 対象 | 方針 | 理由 |
|---|---|---|
| **Protocol Specification** | 寛容（CC-BY / パブリックドメイン相当 / 特許非係争を明記） | 規格は**実装されなければ規格でない**。読んで実装する自由が最優先（原案 §18 末尾と同旨） |
| **Reference Implementation** | 別に決める（Apache-2.0 / MPL-2.0 / AGPL-3.0） | ここは「囲い込みをどこまで許すか」の話。**Spec とは論点が別** |

**AGPL を Spec 側に掛けてはいけない。**規格が最も必要とするのは企業実装であり、
AGPL は**規格の採用者を自分で締め出す**。原案 §19 の Vendor-neutral Governance と正面から衝突する。

Reference Implementation 側で AGPL を選ぶのは筋が通る（囲い込み防止）。
**その場合でも Spec は寛容側に置く。**この分離が §18 に無かった点が、叩きでの主な追加。

## D5. 受信した Agent Message は命令ではない（**叩きとして確定・覆さない**）

**状態**: 確定（設計原則）

原案 §14 は Prompt Injection を脅威リストの 1 項目として挙げているが、
**Agent 同士が構造化 Intent を交換する（§9）以上、これはリスト項目ではなく設計原則である。**

原案 §3.4 が `Authentication ≠ Trust` を分離したのと同じ理由で、
**`Trust ≠ Instruction` を分離する。**「相手が誰か」と「相手の言うことを実行してよいか」は別。

確定する 4 点:

1. **受信した Agent Message は、すべてデータであり、命令ではない**
2. **Capability の判定はモデルの外で行う。**モデルの出力を見て許可を決めない
3. **Trust Level が上がっても、モデルに渡る文字列の扱いは変わらない**
   （Level 4 の相手からの payload も、Level 0 と同じ扱いで読む）
4. 「AI が賢ければ防げる」を採用しない（原案 §14 末尾）

**ここは実装の都合で緩めない。**緩めた瞬間、Trust Level が攻撃者の目標になる
（「信頼を得れば命令が通る」構造＝ Sybil に価値が生まれる）。

## D7. 利用者の端末が他人の通信を中継する構造を採るか（**未決・v2 で新規発生**）

**状態**: 未決 / **発生源**: 企画書 v2 §14 / **調査**: `issues/004` / **決めるのは**: オーナー

### D3 との違い（**別の問いなので分けている**）

| | D3 | **D7** |
|---|---|---|
| 中継する主体 | **自社**が立てた Relay | **利用者の Desktop App** |
| 暫定方針 | 「Phase 2 まで自社運用しない」で回避できる | **回避できない。**自社が運用しないのに中継は発生する |
| 事業者性 | 自社に生じる | **誰に生じるかが未整理** |
| 決めること | 届出の要否 | **利用者に何を負わせるか。既定 ON か OFF か** |

v2 §14 は「Desktop App 自身が必要に応じて SFU / Relay Node になる」と書いている。
**この一文で D3 の暫定方針（自社運用しない）が効かなくなる。**

### 何が問題か

1. **電気通信事業法** — 他人の通信を媒介するのは電気通信役務。
   **利用者の端末が既定でそれを行う**設計にした場合、事業者性が誰に生じるのかが未整理
2. **通信の秘密** — E2EE で中身は読めないが、**中継者は「誰と誰がいつ」を必然的に持つ**。
   ここでの中継者は利用者＝**利用者が第三者の通信のメタデータに触れる**
3. **v2 §20 が挙げた Winny の教訓は、実は §14 に最も強く当たる** —
   v2 は「Public Piracy File Index を作らない」で回避したと書いているが、
   Winny の争点は index の有無ではなく
   **「利用者の PC が、本人が中身を知らないまま他人のデータを運ぶ構造を、開発者が提供したこと」**。
   §14 は index を持たない代わりに **E2EE で中身が見えない**ため、
   **中継者にも運営にも、何が流れているか原理的に分からない**。
   「知らなかった」は成立するが、**止める手段も無い**という状態になる

### v2 が既に出している答え（＝ここが決めどころ）

v2 §14 は Relay Capability に **`Willingness`** を含めている。**利用者の同意を取る前提**である。
**この同意の取り方が、そのまま法的な立て付けになる。**

| 決めること | 選択肢 |
|---|---|
| **既定値** | 既定 ON（回線に余裕があれば自動で中継）/ **既定 OFF（明示的に有効化した人だけ）** |
| **可視性** | 中継していること・量・相手数が本人に見えるか。**見えないなら Winny と同じ構造** |
| **停止** | いつでも即時に止められるか。止めたとき進行中の中継はどうなるか |
| **範囲** | 誰の通信でも中継するか、**自分の Trust Graph 内に限るか**（後者なら「他人」の定義が変わる） |

**最後の「Trust Graph 内に限る」は、法務と技術の両方に効く可能性がある。**
見ず知らずの他人ではなく**自分が信頼を設定した相手の通信だけを中継する**なら、
Winny 型（不特定多数・匿名）とは構造が違うと説明できる余地がある。
ただし**中継可能な Peer が激減する**ため、§14 の Fallback 設計と正面から衝突する。
**技術的な最適と法的な安全が逆を向いている典型。**

### 叩きとしての暫定方針（**覆してよい**）

- **§14 の設計内容は保持する。**捨てない（D8 と同じ扱い）
- **実装順は最後尾**（v2 Phase 7 相当。roadmap の「以降」）
- **他人の通信を中継する機能を、既定 ON にしない**
- **n=2 と Phase 1〜3 では中継が発生しない**ので、**D7 の決着を待たずに着手できる**
  ＝ **これは着手のブロッカーではない**（D2 と違う点）

## D8. Phase 順 — v2 の並び替えを採らず v1 のまま（**叩きとして確定・覆せる**）

**状態**: 叩きで確定 / **発生源**: 企画書 v2 §25

### 何が起きているか

v2 は Phase を 0〜8 に増やし、**Voice/Video を Phase 3、Embedded SFU を Phase 4、
Agent を Phase 5** に置いた（v1 は Phase 3 = Agent）。

**この並びは v2 自身の §22 / §23 と矛盾する。**

| v2 Phase | 内容 | **v2 自身の分類** |
|---|---|---|
| 3 | Voice / Video / WebRTC / TURN | **§22「再発明しない領域」**（Codec・WebRTC・NAT traversal・TURN が全部そこに載っている） |
| 4 | Embedded SFU | **§22「再発明しない領域」**（SFU engine がそこに載っている） |
| **5** | **Agent Identity / Capability / A2A / Calendar Demo** | **§23「独自価値」の 1・5・6・11・12** |

**再発明しない領域に 2 フェーズ費やしてから、独自価値に着手する順**になっている。

**さらに v2 の内部で矛盾がある。**§26「初期 90 日」の Month 3 は
「Agent Identity / Capability / A2A / Calendar Adapter / 双方 Calendar Event 作成 Demo」＝
**Phase 5 の中身**。**Phase 3・4 を飛ばさないと 90 日で到達しない。**

### 確定させること

- **§26 の 90 日プランを正とする**（v1 の Phase 順と一致し、§23 の独自価値を先に取る）
- **v2 §13 §14 の設計内容は捨てない。**Peer Election / Health Metrics / Failover /

## D10. 実装言語と Transport（**未決だったものを確定・覆せる**）

### 決めたこと

| 層 | 採用 | 何を任せるか |
|---|---|---|
| **Transport** | **iroh 1.0**（Rust / QUIC / Apache-2.0 + MIT） | NAT 越え・暗号化路・Relay fallback |
| **コア** | **Rust** | Identity / 鍵 / Profile / Capability / 割符 |

| **デスクトップ** | **Tauri 2** + TypeScript + SvelteKit | 画面 |
| **パッケージマネージャ** | **pnpm**（baseline §1） | |

### 根拠

**① iroh を選ぶ理由 — 「公開鍵でダイヤルする」がそのまま割符である**

iroh は **IP アドレスではなく公開鍵で相手を指定する**。これは D6 で決めた製品名の由来
（割符 = 片割れが合うことで相手を証明する）と、原案 §3.1 / §4（Identity を中央に預けない）を
**そのまま実装した形**になっている。原案 §8 の Adapter 対象に iroh は既に挙がっている。

- **1.0 が 2026-06-15 に出ており、wire protocol の安定が保証されている**（着手時点で破壊的変更の risk が低い）
- QUIC + TLS 1.3 を直接使い、**直接接続が張れた後は Relay が経路から外れる**
- **Node.js / Python / Swift / Kotlin の公式バインディングがある** — スマホ（`issues/003` の n=2）と、
  将来の 2 実装目（D1）の両方に効く

**② シグナリングに他人のインフラを使わない**

WebRTC は SDP / ICE を交換する経路（シグナリング）を別に必要とする。
中央サーバを持たない実装では、BitTorrent tracker や Nostr リレーを流用する方式
（Trystero 等）が一般的だが、**これは採らない**。

理由は 2 つ。**相手が誰かを他人のインフラに教えることになる**のが原案 §21（中央 Directory を作らない）の
主旨と食い違うこと。もう 1 つは、**warifu は既に鍵で相互認証された経路を持っている**ので、
外部に頼る必要がそもそも無いこと。

**SDP / ICE は iroh の E2EE チャネル上で運ぶ。**招待（割符）で 1 度つながれば、以後の会議招集も同じ路を通る。

**③ 音声・映像を自前で書かない**

原案 §8 / §21 と v2 §22 のとおり。Codec・エコーキャンセル・ジッタバッファ・帯域推定は
**再発明しない領域**であり、ここを自前で書くと会議の品質で既存スイートに永久に勝てない。
WebView の WebRTC 実装（＝ブラウザと同じもの）をそのまま使う。

**④ Rust と Tauri 2 を選ぶ理由 — md-business と同じ土台に乗る**

md-business は **Tauri 2 + TypeScript + SvelteKit + pnpm / MIT**（2026-08-17 実測）。
warifu のコアを Rust にすると、iroh をそのまま使えるうえ、
**md-business と同じ形のデスクトップアプリになり、後から同居させられる**。

**ただしこれは「md-business に依存する」ことではない**（→ D11）。

### 採らなかった案とその理由

| 案 | 採らない理由 |
|---|---|
| **libp2p** | 汎用で機能が多い分、今回要らないもの（DHT による探索）が既定で付いてくる。**探索は原案 §21 が明示的に持たないと決めた機能**であり、持たない設計に足すのは筋が悪い |
| **Matrix** | サーバー前提。ホームサーバーを誰かが運用する構造は原案 §3.1 と合わない |
| **Nostr をシグナリングに使う** | 上記②。**リレー運営者に「誰と誰がいつつながったか」が渡る** |
| **TypeScript だけで書く（Rust を使わない）** | iroh の Node.js バインディングは使えるが、**モバイル（Swift / Kotlin）で同じコアを共有できなくなる**。`issues/003` の n=2 がスマホを含む以上、コアは Rust に置くほうが後で効く |
| **Jami を fork する** | 分散 P2P で Voice/Video を実際に動かしている数少ない例だが、**中心が Identity ではなく通話**。warifu は逆（Identity が中心・映像は手段）なので、乗せ替えるより参照するほうが早い |

### これを止めるべき条件

- `issues/001` の残りの調査で、**Identity / Capability 側の結論が別言語を強く指す**場合
  （例: DIDComm v2 の実用的な実装が特定言語にしか無い）
- iroh の Relay fallback が、**n0 社が運用する公開 Relay を既定で使う**点が問題になる場合。
  **直接接続が張れないときだけ経路に入る**が、その間は「誰と誰がいつ」が n0 に渡る。
  D3 の「メタデータの最小化を法務判断より先に設計で決める」に照らし、
  **自前 Relay を立てられる形にしておく**（iroh は Relay を自分で立てられる）

## D12. 割符と鍵の具体（2026-08-17・M1 実装で確定）

`warifu-core` を書くにあたって決めたもの。**自前で暗号を作らないという原案 §8 は守っている**
（使ったのは HKDF・SHA-512・Ed25519 という既存の部品だけで、新しい方式は考えていない）。

| | 採用 | 理由 |
|---|---|---|
| 鍵の導出 | **HKDF-SHA512** | 標準（RFC 5869）。シード 1 個から用途ごとの鍵を出す用途そのもの |
| 署名 | **Ed25519**（`ed25519-dalek` 2.2） | 鍵 32 byte・署名 64 byte と短い。QR に入る。iroh の NodeId も Ed25519 なので**同じ鍵で名乗れる** |
| 文字列表記 | **base32（RFC 4648・大文字・パディングなし）** | 16 進より短い。Base64 と違い記号が入らないので、読み上げ・手入力・QR で壊れにくい |
| 割符の運搬 | **バイト列 141 byte / 受諾 173 byte（固定長）** | 長さが固定だと、余分な後ろ付けをそのまま弾ける |

### 決めたことのうち、後で効くもの

**1. すべて決定的に導く（シード 32 byte → Profile → Device）**

同じシードからは、いつどの端末で計算しても同じ鍵が出る。
これにより **D2（鍵の復旧方式が未決）が実装のブロッカーから外れた** — 復旧方式が
紙・Social Recovery・端末バックアップのどれになっても、**戻すものは 32 byte で変わらない**。

**2. ラベルを長さ付きで混ぜる**

`"a" + "b"` と `"ab" + ""` が同じ入力になると、ラベルを細工して他人の鍵を作れてしまう。
長さを前に置いて区切りを跨げなくした（テストで固定）。

**3. 受諾では秘密そのものを返送させない**

割符の片割れは warifu の外（QR・貼り付け）を通る。
受諾に秘密をそのまま入れると、**経路を覗いていた者が横から同じものを名乗れる**。
入れるのは「秘密を知っている証」（秘密 + 相手の公開鍵 + 時刻のハッシュ）だけにした。
照合は定数時間で比較する（早く抜けると 1 byte ずつ当てられる）。

**4. 失効は取り消せない**

降ろせる仕組みを作ると、**鍵を盗った側が降ろせてしまう。**
戻したいときは新しい鍵を作る（＝新しい割符を配り直す）。
失効させた時刻は最初の 1 回だけを残す（上書きすると、いつ失くしたかが消える）。

**5. 時刻は相手を信用しない**

受諾に入っている時刻は相手の申告でしかない。期限は**照合する側が自分の時計で**もう一度見る。

### これを止めるべき条件

- **Ed25519**: iroh を外す決定（D10 の見直し）が出た場合、同じ鍵で名乗れる利点が消えるので選び直す
- **base32**: QR ではなく別の受け渡し（NFC・近接音）が主になった場合、表記そのものが不要になる
- **固定長のバイト列**: 会議で扱う項目が増えて可変長が要るようになったら、
  そのときに**版番号（先頭の `WRF1`）を上げて別の形にする**。既存の割符は読めるまま残す

## D13. 経路の具体（2026-08-17・M2 実装で確定）

`warifu-net` を書くにあたって決めたもの。**D10（iroh 採用）の中で、実際にどう使うか**を固定した。

| | 採用 | 理由 |
|---|---|---|
| iroh の版 | **1.0.3** | 1.0 で型名が `NodeId` / `NodeAddr` → **`EndpointId` / `EndpointAddr`** に変わっている。古い記事のまま書くと通らない |
| 起こし方 | **`presets::Minimal` + `RelayMode::Disabled`** | 暗号の実装だけを取り、**n0 の DNS も中継も使わない**。回線が無くてもテストが走る |
| 鍵 | **端末の Ed25519 鍵をそのまま QUIC の鍵にする** | `EndpointId == warifu の PublicKey`。**別の鍵で繋ぐと、割符で確定した相手と実際に繋がった相手が別物になる** |
| 宛先の表記 | **`WARIFU1-` + base32**（目印 `WRFA`） | 割符（`WRF1`）と頭を揃え、中身の種別で分ける。**warifu が外に出す文字列は全部 base32 を通る** |
| 塊の切り方 | **長さ 4 byte（BE）を前に置く。上限 16 MiB** | 切れ目を決めないと、受け取る側は「どこまでが 1 つか」を当てられない。上限は**長さだけ大きく宣言して確保させる攻撃**を止めるため |

### 決めたことのうち、後で効くもの

**1. 中継を既定で使わない（D10 の「既知の問題」を 1 つ閉じた）**

M1 時点の記録には「iroh の既定 Relay で、誰が誰に繋いだかが n0 側に出る」と残していた。
M2 では `bind_without_relay` しか作っていない。**中継を挟む口はまだ開けていない。**

代わりに、**相手と直接つながらない回線（対称 NAT・厳しい社内網）では繋がらない。**
これは伏せずに残す。中継が要ると判明した時点で、**自前 Relay かどうかを D3 と一緒に決める。**

**2. 失効は呼ぶ側と受ける側の両方で見る**

名簿は各自の手元にある。呼ぶ側だけで見ると、**受ける側は「相手の名簿が正しい」に賭けることになる。**
逆に受ける側だけで見ると、失くした自分の端末を自分から呼びに行く。

**3. 送れたことは、届いたことではない**

`send()` が返るのは「送る列に積んだ」ところまで。**積んだまま経路を落とすと、まだ網に出ていない分は消える。**
送り終わりだと分かっているなら `finish()` を呼ぶ（相手が受け取り切るまで待つ）。

これは実際にテストが 20 秒待って落ちて分かった。**先に知っていたわけではない。**

**4. 呼びに行くのに上限を切る（10 秒）**

宛先の公開鍵だけ他人のものに差し替えられた場合、**下の層は「届かない」としか分からない**
（経路探索の packet が名乗った鍵で暗号化され、本当の持ち主に捨てられるため）。
iroh は繋がるまで試し続けるので、**上限を切らないと呼んだ側が永久に待つ。**

### これを止めるべき条件

- **中継なし**: 実測（M6）で、普通の家庭回線同士が繋がらない割合が無視できないと分かったら見直す
- **`presets::Minimal`**: 公開鍵だけで相手を見つけたい（宛先の文字列を渡さずに済ませたい）となったら、
  そのときに**何が外に出るか**を D10 と一緒に読み直す
- **16 MiB**: 会議の画面共有や動画がこの口を通ることになったら、**塊で送るのをやめて流し込みに変える**

**2026-08-17 決定。**

### 決めたこと

`warifu-intent` を M2 の上に載せた。1 通ぶんの形は**これだけ**。

```text
  [0]        口の名前の長さ（1..=64）
  [1..]      口の名前（小文字・数字・点。`file.offer` など）
  [..+16]    相関（どの話の続きか）
  [残り]     荷物（**warifu は読まない**）
```

### 根拠

**1. 口の名前は「名前空間 . 動作」の正規形しか受け取らない**

小文字・数字・点だけ。点は区切りとしてしか置けない（`..` も先頭・末尾の点も弾く）。
表記が 2 通りあると、同じ口が別物として通る。`..` を弾くのは、
**名前がそのままパスとして使われる日**を作らないため（受け手が名前でファイルを置く実装をしても壊れない）。

warifu が意味を知っているのは `file.*` と `meeting.*` の 9 つだけ（D11 が定めた担当範囲）。
`invoice.*` は md-business の領域なので入れていない。

**2. 知らない口も通す。ただし「知っている」とは言わない**

`Kind::is_known()` は false を返すが、経路は落とさない。
版が 1 つずれただけで繋がらなくなると、**新しい方を出せなくなる。**

**3. 受け取っても実行しない（D5）**

この層には「受け取ったら実行する」口が 1 つも無い。`Channel::recv` は読める形にして返すだけ。
開くか・保存するか・捨てるかは呼ぶ側が決める。

**4. 荷物には長さを書かない**

切れ目は経路（`warifu-net`）が既に決めている。ここでもう一度長さを書くと、
**2 つの長さが食い違ったときに、どちらが正しいか決められなくなる。**
代わりに「荷物の途中で切れたこと」はこの層では分からない。それでよい（切れれば下で落ちる）。

**5. `Debug` に荷物の中身を出さない**

荷物は文書そのもの。ログに落ちれば、経路を暗号化した意味が消える。
出すのは口の名前・相関・**何バイト来たか**まで。

### M2 側で 1 つ直した — 経路が結び目を生かす

`Session` を持ったまま `Node` を落とすと、**結び目が閉じて経路も道連れになっていた。**
そのとき送った側には成功が返り、受ける側は永久に待つ。**落ちたことにすら気づけない。**

M3 のテストが 20 秒待って落ちて分かった。`Session` が `Endpoint` を 1 つ持つように直し、
`結び目を落としても経路は生きている` で固定した。**M3 を書かなければ M2 のまま残っていた。**

### これを止めるべき条件

- **口の名前 64 バイト**: 足りなくなったら、それは名前ではなく荷物に入れるべきものが混ざっている
- **相関 16 バイト**: 同時に走る話が桁違いに増え、取り違えが起きたら見直す
- **知らない口を通す**: 実際に「知らない口を送りつけて相手を止める」使われ方が出たら、名前空間ごとの許可制にする

## D15 — 会議は「名簿」と「段」だけを持ち、SDP は読まない（M4）

**2026-08-17**

`warifu-meeting` を `warifu-intent` の上に載せた。運ぶのは 4 種類だけ。

| 口 | 荷物 | 相関 |
|---|---|---|
| `meeting.invite` | `[人数 1][鍵 32]*人数` | 会議 id |
| `meeting.join` | **空** | 会議 id |
| `meeting.leave` | **空** | 会議 id |
| `meeting.signal` | `[段 1][SDP / ICE そのまま]` | 会議 id |

### なぜこの形にしたか

**1. 4 人という上限をコードに固定した（`MAX_PARTICIPANTS`）**

5 人以上にすると誰かの端末が他人の映像を中継することになり、それは **D7** そのもので
法的な決着が付いていない。**「運用で気をつける」にしない。**
送る側だけでなく **受け取る側でも数える**（相手が上限を守る保証は無い）。

**2. 会議 id をそのまま相関にした**

別に会議 id を荷物へ書くと、相関と食い違ったときに直しようがなくなる（D14 の「長さを二重に持たない」と同じ理由）。
おかげで `meeting.join` / `meeting.leave` の荷物は空にできた。

**3. 下ごしらえに宛先欄を作らなかった**

宛先欄があると「自分宛でない下ごしらえを預かって渡す」形が書けてしまう。
それは **D7 への入口**。フルメッシュでは相手ごとに経路が 1 本ずつあり、
**誰宛かは経路そのものが決めている。**

**4. SDP / ICE を解釈しない**

見るのは段（申し出・返事・候補・終わり）の 1 バイトだけ。中身はバイト列として素通しする。
読み始めると Codec の話が warifu に入り込み、**「Codec を自前で書かない」が守れなくなる**（`issues/005` 満たすこと 3）。

**5. 段は 4 つで閉じる。口は開けておく**

知らない `Kind` は通す（D14）が、**知らない段は弾く**。
口は増やせる場所として開けてあり、段は決まりきった手順。
知らない段を「たぶん申し出だろう」と扱うと繋ぎ間違える。

**6. 下ごしらえに 64 KiB の上限を別に置いた（`MAX_SIGNAL`）**

経路の上限は 16 MiB だが、SDP は普通は数 KB。
**16 MiB の「SDP」を送りつけられて確保させられる筋**をここで塞ぐ。

**7. `Debug` に中身を出さない**

SDP と ICE には**端末のローカル IP が入っている**。ログに落ちれば、
直接つながる相手以外にも住所が漏れる。出すのは段と何バイト来たかまで。

### まだ開いている問い

**3 人目・4 人目が、他の参加者の「住所」をどう知るか。**
名簿が運ぶのは公開鍵だけで、経路の当てはまだ入っていない。
M6（3〜4 人のフルメッシュ）で決める。M4 を大きくしない（baseline §7）。

### これを止めるべき条件

- **4 人**: M6 の実測で手元の回線が持たなければ **3 に下げる**。上げる側には D7 の決着が要る
- **段 4 つ**: WebRTC 側で足りない段が出たら足す。ただし**足したことが分かる形**で（知らない段は今も弾く）
- **64 KiB**: 実際の SDP が近づいたら見直す。**上限を外す選択はしない**

## D17. 品質ゲートを CI に置く（**確定・実行環境の実測に基づく**）

**状態**: 確定（2026-09-01）/ **決めたのは**: このリポジトリ / **覆せる**: 手元のゲートが全開発機で成立するようになったとき

### 何が起きたか

2026-09-01 のセッション開始時に開発機の実測を取ったところ、
**`cargo` と `rustc` が入っていなかった**（`~/.cargo` / `~/.rustup` ごと無い）。
`pnpm` も無く、`node` は v20.5.0（`project-status.md` の記録は v22.22.2）。

つまり **M1〜M4 を書いた環境と、今動いている環境が違う**。
「`cargo test` 105 件 green」は**別の機械での実測値**であり、手元で再現できない。

さらに `.github/workflows/` には `oss-privacy-check.yml` しか無く、
**test / clippy / fmt を回す CI が存在しなかった**。git hooks も未設定。

**手元のゲートも無く、CI のゲートも無い**状態だった。

### 決めたこと

**`.github/workflows/rust.yml` を最終ゲートとして置く**（fmt → clippy → test）。

- 第三者の action を足さない（`actions/checkout` と `actions/cache` のみ）。
  ゲート自身が依存を増やすと、ゲートの信頼性がその依存に乗る（§12）
- `rustup` は runner に入っているものを使い、**component だけ明示して入れ直す**
- `concurrency` で古い実行を打ち切る。**結果が 2 つ出ると、どちらが今か分からなくなる**

### なぜ hooks を先に入れないか

§5 は「commit 前に lint / typecheck / test が走る仕組み」を求めており、hooks はその第一候補である。
だが **hooks は `cargo` が無い機械では成立しない**。今まさにそういう機械で動いている。

**入り口（hooks）より先に、最後の関所（CI）を作る。**
hooks は「速く気づくための道具」であって、**通ったことを保証する主体ではない**。
順番を逆にすると、`cargo` が無い機械では hooks が黙って素通りし、
**ゲートが有るように見えて何も見ていない**状態になる。

hooks は、開発機にツールチェーンが揃った時点で足す。

**2026-09-02 追記 — 足した。**`.githooks/pre-commit` と `scripts/setup-hooks.sh`。
順序は個人情報 → fmt → clippy → test で、**個人情報の検査だけは cargo が無くても必ず走る**
（public リポで一番戻せない失敗だから・baseline §25）。

素通りへの手当てを 2 つ入れた。

- **cargo が無いときは、黙らずに大きく言う。**「実行できませんでした」と出したうえで通す
  （§5 の「手元のゲートが壊れたことを理由に止めない」）
- **`$HOME/.cargo/bin` を PATH に補う。**git を起動したのがログインシェルとは限らない
  （GUI クライアント・エディタ内の git）。補わないと、**cargo があるのに「無い」と判定して
  黙って素通りする** — D17 が言っているのは、まさにこの形の壊れ方である

`--no-verify` の回避手順は書かない。**今回だけ外した手順は、次からの既定になる**（§18）。

### 採らなかった案

| 案 | 採らない理由 |
|---|---|
| AI が `rustup` を入れて手元を直す | **開発環境の構成は人の領分。**勝手に入れると次のセッションの前提がずれる（§29）。**→ 同日中に指示で覆った。下記の追記を見ること** |

### これを止めるべき条件

- CI 実行時間が長くなりすぎて、**落ちたことに気づくのが遅れる**ようになったとき

## D18. `warifu-read` — 受け取ったものを AI を呼ばずに読む層の形（**確定・R1 の範囲**）

**状態**: 確定（2026-09-01）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

`issues/007` / roadmap Phase 3-b の実装にあたって決めたこと。R1（既定と段）の範囲。

### 1. 依存を 1 つも持たない

`warifu-read/Cargo.toml` の `[dependencies]` は**空**。
`warifu-net` にも `warifu-intent` にも依存しない。

この層の値打ちは **相手も鍵も経路も要らない**ことにある（`issues/007`）。
通信層に依存させた瞬間、「IMAP だけで動く」が嘘になり、
**n=1 で効く唯一の層**という性質が消える。依存の無さは、そのための構造である。

### 2. 「Level 0 に本文を入れない」を**判定ではなく型**で守る

`View::Metadata(Metadata)` の `Metadata` に、**本文が入る場所が無い。**

実行時の判定にすると、いつか判定を通さない経路ができる。
`issues/007` の完了条件が「テストで確認している」なのに対し、
**ここは型で先に閉じてある**（テストは表示側の漏れを見ている）。

### 3. 解釈器（LLM）を**このクレートに入れない**

要約と構造化を求められたとき、この層は `Error::NeedsInterpreter` を返して**止まる。**
黙って要約を作らない。**作るなら AI を呼ぶことになり、目的が最初に消える。**

呼ぶかどうかは呼ぶ側が決める（**D5**）。R2 で規則が育てば、
同じ形式の 2 通目からはこれが返らなくなる — それがこの層の目的そのものである。

**「まだ作っていない」（`NotBuiltYet`）と混ぜない。**
添付の組み立ては解釈器を呼べば出るものではないので、別の失敗にした。
混ぜると「AI を呼べば解決する」と読める失敗が増える。

### 4. 送信者の申し送りは**捨てずに持ち、判断には使わない**

`Claims` として保持し、`Metadata` の組み立てでは 1 度も見ない。

捨てないのは、**後から人が「何を無視したか」を見られるようにするため。**
無視した事実が残らないと、無視が正しかったかを誰も確かめられない。

`Claims` の `Debug` は件数しか出さない。**相手が書いた文字列をログへ素通しすると、
読む前に読むことになる。**

### 5. 送信元の照合は**完全一致**

大文字小文字を潰さない。潰すと `Billing@例` と `billing@例` が同じ規則に当たる。

**当たらない側に倒す。**当たらなければ解釈器を 1 回余計に呼ぶだけで済むが、
取り違えれば別の送信元の規則で読むことになる。**損の大きさが違う。**

### 覆してよい条件

- **1 と 5 は覆さない。**依存を足すか照合を緩めるなら、それは別の層である
- 2 について、Level 1 / 2 を実装したときに `Metadata` を包む形が窮屈になるなら、
  **型で守る方針は保ったまま**構造だけ見直す
- 3 について、`NeedsInterpreter` が返る割合が実測で下がらないなら、
  **規則の作り方（R2）が間違っている**という信号として読む。層の形の問題ではない

### R1 で作っていないもの（**まだ完了ではない**）

規則（Deterministic Parser・R2）/ token の会計（R3）/ 重複除去とスレッド圧縮（R4）/
IMAP の取り込み（R5）/ Action Inbox。
`issues/007` の完了条件 6 つのうち、**満たしたのは 1 つだけ**。

## D19. 規則は**生成と適用を分ける**（**確定・R2**）

**状態**: 確定（2026-09-01）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

`issues/007` の中心は「**一度学習した形式は二度と LLM を呼ばない**」だが、
同じ Issue が **D5** として「**規則を受信内容から自動生成して自動適用しない**」と書いている。

この 2 つは、そのままでは両立しない。**学習とは、受信内容から規則を作ることだからである。**

### 決めたこと

**生成はしてよい。適用の手前に人を挟む。**

```
  解釈器 ──▶ RuleDraft（候補）──▶ 【人が承認】──▶ Rule（棚に入る）──▶ 読み取りに使う
                                      ▲
                              ここだけが規則を増やせる口
```

- `RuleDraft` は**それ自体では読み取りに使われない**。棚に入らない限り当たらない
- 棚を増やせるのは `RuleStore::approve` **1 本だけ**。
  受信本文からこの口が呼ばれる経路は、この層のどこにも無い
- **`approve` を自動で呼ぶ実装を書かないこと。**書いた時点で D5 が崩れる

### なぜこの形か

「この形式はこう読め」と本文に書いておけば読み手を乗っ取れる、が防ぎたいことの全部である。
乗っ取りが成立するのは **生成と適用が地続きのとき**だけなので、**そこを切る。**

承認は**形式ごとに 1 回**で、通数には比例しない。
請求書・予約確認・配送通知・CI の失敗通知は送信元ごとに形が固定されているため、
**承認の回数は現実的な数に収まる**（それが `issues/007` の前提でもある）。

### 規則に書けることを、抽出だけに絞る

`Extract` が表現できるのは「**ある目印の後ろを取る**」だけ。

条件分岐も、外部呼び出しも、他の規則の書き換えも書けない。
**抜くこと以外を書けないので、規則が命令になりようがない。**
承認する人が読んで判断できるのも、表現力をここまで削ったからである。

補助として決めたこと（いずれもテストで固定した）:

- **当たるのは最初の 1 箇所だけ。**2 箇所目を拾うと、本文を足すだけで抽出結果を動かせる
- **抜けなかった項目は空のまま返す。**`—` や `N/A` で埋めない（baseline §19）。
  埋めると、抜けなかったことが誰にも見えなくなる
- **先に承認された規則が勝つ。**後勝ちにすると、規則を足しただけで既存の読み方が黙って変わる
- **目印はすべて含まれたときだけ当たる。**同じ送信元でも形が変われば別物として扱う

### 残っている穴（**塞いでいない。塞いだふりもしない**）

**送信元は詐称できる。**IMAP の `From` は誰でも書ける。
規則が送信元で当たる以上、**詐称した相手には、その規則で読まれる。**

今この穴が致命傷にならないのは、**規則が抽出しかできないから**である。
読み違えた項目が画面に出るだけで、何も実行されない。

**規則に実行を足すなら、この穴を先に塞ぐこと。**
塞ぎ方は署名の検証（PRD §12-2 の `signature verification`）で、**Phase 3 の実装項目**にあたる。

### 覆してよい条件

- 承認の回数が実測で多すぎたとき。**そのときも自動承認にはしない。**
  まとめて承認する形（同じ形式の候補を束ねる）を先に試す
- `Extract` の表現力が足りず、承認された規則が使い物にならないとき。
  **足すのは抽出の書き方であって、抽出以外の機能ではない**

## D20. 会計と保存は**減らせない形**にする（**確定・R3**）

**状態**: 確定（2026-09-01）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

`issues/007` の完了条件は 6 つのうち 2 つが**記録**についてのものである。
「2 通目で LLM 呼び出しが 0 回であることを**記録で**確認できる」
「1 通あたりの token・呼んだか・規則ができたかが**ローカルに残る**」。

**振る舞いが正しいことと、正しいと示せることは別。**この層は後者を持たないと、
効いているかどうかを誰も言えない。

### 決めたこと

| | 決めたこと | なぜ |
|---|---|---|
| 帳簿 | **消す口を置かない**（追記だけ） | 消せると、掛かった費用を後から減らせる。**失効の名簿を取り消せなくしたのと同じ理由**（`warifu-core` の `Revocations`） |
| ファイル | **追記であって上書きではない** | 上書きだと、前回までの記録が黙って消える |
| 読み込み | **読めない行があればそこで失敗する** | 黙って捨てると「呼んだ回数」が後から減る。**規則の側も同じ**（当たるはずの規則が静かに消える） |
| 本文 | **記録に入れない** | Level 0 で本文を返さない層が、会計から漏らしていたら意味が無い |
| token | **呼んだ側が申告する** | この層は解釈器を持たない。**持たないものを数えられるふりをしない** |
| 種別 | **解釈器を呼んだ行は `unknown` のまま** | 呼ぶことになったのは読めなかったから。**後から分かった種別を遡って書かない** |
| 形式 | **TSV** | baseline §19。表計算で開けるので、**人が実測値を書き足せる**（最後の完了条件は人が書く） |

### 制御文字を弾く

`SenderId` と、承認する規則の目印・抽出から**制御文字を弾く**。

TSV は 1 行 1 項目なので、タブや改行が通ると**1 行を 2 行に割れる**。
割れれば、記録も規則も**偽造できる**。

弾く場所は入口（`SenderId::new`）と承認（`RuleStore::approve`）の 2 つ。
**書き出すときに弾く形にしない** — 棚に入った時点で保存できないと分かっているものは、
入れる前に断る。

### 規則を保存する理由

**「一度学習した形式は二度と呼ばない」は、残って初めて成立する。**
保存しなければ、再起動のたびに解釈器を呼び直す。それでは token は減らない。

### 覆してよい条件

- TSV では表しきれない規則が要るようになったとき。
  **そのときも人が読める形式であることは変えない**（承認できなくなる）
- 帳簿が大きくなりすぎたとき。**消すのではなく、期間で分けて退避する**（baseline §24）

## D21. 重複除去に hash を使わない（**確定・R4・企画書への異議**）

**状態**: 確定（2026-09-01）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

`issues/007` は Deduplication を「署名・免責文・ロゴ・引用ブロックを **hash で除外する**」と書く。
**hash を使わず、原文どうしを比べることにした。**

### なぜか

**hash にすると、衝突を作れる相手が、読み手から任意の 1 ブロックを消せる。**

除去の判定が「hash が既出のものと一致するか」なら、
既出ブロックと同じ hash になる塊を送りつけた側は、**自分の書いた塊を読み手に見せないでおける。**
消えたことは読み手に見えない。**気づきようがない。**

暗号学的 hash なら現実には作れないが、`warifu-read` は**依存を 1 つも持たない層**である（**D18**）。
sha2 を足すのは D18 の 1 番目を覆すことになり、
かといって非暗号 hash（FNV 等）は衝突を**簡単に作れる。**

**突き合わせる数は、1 つの話に出てくる塊ぶんしかない。**
原文どうしの比較で速さが問題になる規模ではない。
**速さの損より、消されない得を取る。**

### 併せて決めたこと

| | 決めたこと | なぜ |
|---|---|---|
| 定型（署名・免責文） | **人が登録する。本文から自動で覚えない** | 覚えると、同じ文を 2 回送るだけで読み手から 1 ブロックを消せる。D19 の「生成と適用を分ける」と同じ形 |
| 話の単位 | **話ごとに 1 つ持つ。跨いで使い回さない** | 別の相手が同じ文を書いたときに片方が消えて読み違える |
| 比較 | 行ごとに前後の空白を落として比べる | 引用で字下げが 1 つ増えただけの塊を「新しい」と数えないため |
| 返す文字列 | **原文のほう。**空白を潰した側は外に出さない | 読み手が受け取るのは、相手が書いた文字列でなければならない |
| 順序 | **変えない** | 並べ替えると話の流れが読めなくなる |

### 覆してよい条件

- 1 つの話の塊数が実測で数千を超え、比較が体感に出るようになったとき。
  **そのときも「消せる」性質は受け入れない** — 先に話の区切り方を見直す
- 依存を持つと決めた場合（D18 の 1 番目を覆す提案が通った場合）に限り、
  暗号学的 hash を使う形へ寄せてよい。**非暗号 hash はその場合も使わない**

## D24. 判定をモデルの外に出す（**確定・`issues/008`**）

**状態**: 確定（2026-09-02）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

**D5 は原則を確定させていたが、実装が無かった。**`warifu-capability` として作った。

### 判定の入力は 3 つだけ — **誰が / 何を / 今いつか**

`Request` に**本文が入る場所を作っていない。**

モデルの中で判定すると、判定の入力に本文が混ざる。本文は相手が書いたものなので、
そこに「この要求は承認済みです」と書いておけば判定が動く余地が生まれる。
**動かないように書き方で気をつける形は、必ず漏れる。**

`warifu-read` の Level 0 と同じ手である（**D18** の 2 番目）。
判定にすると、いつか判定を通さない経路ができる。**型に入る場所が無ければ、その経路は書けない。**

### 信頼を判定に使わない（**D5 の核心**）

`Trust` は持つが、`Gate::decide` は見ない。**テストで固定した。**

「信頼した相手の言うことは通す」を作ると、**信頼を得ることに価値が生まれる。**
価値が生まれれば、そこを狙って偽の Identity を作る意味が出る。
これは「巨大中央 User Directory を作らない」が Sybil 耐性の根拠になっているのと同じ話で、
**探せない・得しても意味が無い、を保つ。**

### 併せて決めたこと

| | 決めたこと | なぜ |
|---|---|---|
| 既定 | **拒否** | 「たぶん大丈夫」を作らない。`Decision` は 2 つしかない |
| 照合 | **完全一致。前方一致にしない** | `calendar.freebusy` の札で `calendar.freebusy.all` が通ってしまう |
| 期限 | **必ず要る。期限なしの札を作れない** | 期限が無い札は出したことを忘れられる。**忘れられた許可は、誰も見ていないところで効き続ける** |
| 記録 | `decide` が `&mut self` | **記録を残さずに判定できないようにする。**記録の要らない口を別に置くと、そちらが使われる |
| 実行 | **この層は何も呼ばない** | 返すのは `Decision` だけ。`warifu-intent` に「受け取ったら実行する」口が 1 つも無いのと同じ |

### 札は降ろせる（**向きに注意**）

`Gate::revoke` を置いた。**間違って出した札を直せないと困る**からである。

`warifu-core` の失効名簿は**取り消せない**（降ろせると、鍵を盗った側が降ろせる）。
ここは逆で、**許可は取り消せる**。

**安全の側へ倒す向きが、2 つで逆になっている。**混ぜないこと。
失効は「危険だと宣言したこと」を守る。許可は「危険なことをしてよい」を減らせるようにする。

### この Issue に含めなかったもの

実際に tool を呼ぶ部分 / Calendar・MCP など具体的な相手 / Trust Graph の育て方。
**関所は「よい / だめ」を返すだけ**にして、呼ぶ側と分けた。

### 覆してよい条件

- 完全一致では札が増えすぎると分かったとき。
  **そのときも前方一致にはしない** — 札をまとめる別の形（範囲を持つ札）を先に検討する
- `Trust` を判定に使いたくなったとき。**これは覆さない。**
  使いたくなった時点で、D5 が塞いだ穴を開けようとしている

## D25. MCP の口は関所の内側に置く（**確定・`warifu-mcp`**）

**状態**: 確定（2026-09-02）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

オーナー指示: 「**MCP の拡充も必要。まるで人かのように操作できることが AI ドリブンな未来**」。

**その通りに作った。ただし置き場所を関所の内側にした。**

### 「人のように操作できる」ことと「人の代わりに決められる」ことは別

AI が受信箱を人のように扱えることが、この口の目的である。
**だが、何をしてよいかを AI が決めてよいわけではない。**

だから `warifu-mcp` の tool から**関所を迂回する経路を 1 本も置いていない。**
呼べば必ず `Gate::decide` を通り、通らなければ何も返らない。
これが PRD §12-2 の「**モデルから直接 tool を呼ばせない / policy engine 経由**」にあたる。

### 承認の口を tool にしない（**一番大事**）

規則の承認（`RuleStore::approve`）も札の発行（`Gate::issue`）も、**tool にしていない。**

出した時点で、**AI が自分に許可を出せる。**
生成と適用を分けた意味（**D19** / **D24**）が、そこで消える。

**テストで固定した** — 口の名前に `approve` / `issue` / `grant` / `revoke` / `trust` を
含むものが 1 つも無いこと、口が 3 つしか無いこと。
口を増やすときは、**その口に札の種類が要るかを先に決める。**
札の要らない口を 1 つ足した時点で、関所を迂回する経路ができる。

### 段ごとに別の札

`inbox.list` / `inbox.open.summary` / `inbox.open.structured` / `inbox.open.raw` /
`inbox.open.attachments` / `rules.list` は**すべて別の札**である。

関所の照合が完全一致（**D24**）なので、これは自動的に成り立つ。
「一覧を見てよい」は「本文を読んでよい」ではない。

### 断る理由に、通し方を書かない

`Decision::Deny` のとき返すのは動作名だけで、**どうすれば通るかは書かない。**
書くと、断られた側が総当たりで札の形を探れる。

### 依存

| crate | 版 | 最終更新 | DL/月 | license |
|---|---|---|---|---|
| `rmcp`（公式 Rust SDK） | 3.2.0 | **2026-08-31** | 11,982,550 | Apache-2.0 |

**+20 crate。**自前で JSON-RPC の部分集合を書けば +3 で済むが、
**MCP は動いている仕様**で、版の交渉も含めて追い続けることになる。
Transport と暗号を再発明しないのと同じ理由で、ここは SDK に寄せた（原案 §8）。

採らなかったもの: `mcp-core` 0.1.50（**最終更新 2025-05-01**・DL/月 5,768）。

**`warifu-read` と `warifu-capability` には足していない。**
あの 2 つは依存ゼロのままで、MCP は外側の 1 クレートに閉じている（**D18** / **D22** と同じ形）。

### **実際に繋いで確かめた**

`warifu-imap`（D23）と違い、**ここは実物のやり取りを通してある。**


### 覆してよい条件

- `rmcp` が更新されなくなったとき（**現時点で最終更新は前日**）
- 口を増やしたくなったとき。**増やしてよいが、札の種類を先に決める。**
  「とりあえず札なしで出す」を 1 回でもやると、この層の意味が無くなる

## D26. 予定表は「空いているか」しか外に出さない（**確定・Phase 3 の代表 Demo**）

**状態**: 確定（2026-09-02）/ **決めたのは**: このリポジトリ / **覆せる**: 下記の条件で

企画書 v2 §17 の会議調整。roadmap **Phase 3** が「Capability の実地テストになる」と
書いていた所を実装した。

### なぜここが実地テストになるか

**見せてよいものと見せてはいけないものが、同じ予定表の中に混ざっている。**

「空いているか」は渡してよい。「何の予定か」は渡してはいけない。
1 つの予定表から両方を出そうとすると、**どこかで題名が付いてくる経路ができる。**

だから `Calendar::slots` は `Span` しか返さない。**題名が入る場所が無い**
（`warifu-read` の Level 0・`warifu-capability` の `Request` と同じ手）。
`Event` の `Debug` も題名を伏せる。

### 空き枠を返すことは、埋まっている時間を教えることでもある

**これは避けられない。**空き枠が分かれば、その裏返しが埋まっている時間である。
消せない以上、**一度に見える範囲を絞る**方向で扱う。

| | 決めたこと | なぜ |
|---|---|---|
| 窓 | **31 日まで**（`MAX_WINDOW`）。超えたら断る | 広く取れるなら、尋ねるだけで**予定表を丸ごと写し取れる** |
| 件数 | **上限はこちらが決める。**MCP の引数に入れない | 相手に決めさせると、絞った意味が無い |
| 長さ | 求めた長さに満たない隙間は返さない | 使えない枠を数えても仕方がない。**細切れの情報だけが余分に出る** |

**予定表が空なら「ぜんぶ空いている」と答える。**これは正しい振る舞いだが、
同時に「予定が 1 つも無い」と教えてもいる。**そこも上の 3 つで絞る以上のことはできない。**

### 片方だけでは確定しない

`Coordination` は**双方が同じ枠を承認したときだけ**確定する。

片方の Agent が勝手に予定を入れられるなら、
**予定表は相手の Agent に開放されているのと同じ**である。

- 承認は**候補の中からしか選べない**（候補の外を通せるなら、候補を出した意味が無い）
- **何度でも変えられる。**間違えて押したときに直せないと、人は押すのを怖がる
- **断れば、確定していても取り消せる**

### 断り方を 2 つに分ける

MCP の口では、**「札が無い」と「窓が広すぎる」を同じ言い方にしない。**

```text
札なし          → 関所が断りました: inbox.list
窓が広すぎる    → 出せません: 尋ねる窓が広すぎます
```

混ぜると、**札を足せば直るのか、直しようが無いのか**が呼ぶ側に分からなくなる。
（実際のやり取りで確認済み。）

### 覆してよい条件

- 31 日では業務に足りないと分かったとき。**そのときも「上限なし」にはしない**
- 予定の中身を相手に見せたくなったとき。**これは覆さない。**
  見せたいなら、それは空き時間の仕組みではなく**別の共有**であり、別の札が要る

## D27. 会議の定員は会議ごとに決める（**確定・D9 の一部を置き換える**）

**状態**: 確定（2026-09-02）/ **決めたのは**: オーナー判断 ＋ 本リポジトリの訂正 / **覆せる**: 下記

### 何を直したか

D9 は「複数人ビデオ会議を **4 人まで**と定義する」とし、`MAX_PARTICIPANTS = 4` を
コードに固定していた。理由として **D7**（利用者の端末が他人の通信を中継する）を挙げていた。

**この理由付けは誤りだった。**

| | D9 の書き方 | 実際 |
|---|---|---|
| 5 人フルメッシュ | 「誰かの端末が他人の映像を中継する＝ D7 に触れる」 | **触れない。**各自が**自分の映像だけ**を全員へ直接送る。誰も他人の通信を運ばない |
| 効いている制約 | 法的（D7） | **帯域。**上りが参加者ごとに `K×(N−1)` |

D9 は「5 人以上 ＝ SFU が要る」という**実務的な仮定**を、そのまま**法的な線**として書いていた。
SFU が要るのは帯域が足りないときであって、**人数が 5 になった瞬間ではない。**

**混ぜてはいけない 2 つを混ぜていた。**

### 決めたこと

- `MAX_PARTICIPANTS = 4`（固定）を廃止
- **`DEFAULT_CAPACITY = 4`** — 定員を指定しないときの既定。**上限ではない**
- **`HARD_LIMIT = 16`** — フルメッシュとして成立しうる外枠
- `Roster::with_capacity(host, n)` で**会議ごとに定員を決める**（`2..=HARD_LIMIT`）

**1 人の会議は作れない。**会議として成立しない。

### なぜ外枠を 16 に置くか

**外枠そのものは要る。**無いと、招待に書かれた定員をそのまま信じることになり、
巨大な数を名乗る招待で確保させられる。

16 の根拠は帯域である。720p を 1.5 Mbps とすると、
16 人フルメッシュで上り 22.5 Mbps・下り 22.5 Mbps。
**家庭用の光なら届くが、携帯回線では無理**という辺り。

**これを超えたいなら、誰かが他人の映像を運ぶことになる。そこで初めて D7 の決着が要る。**
D7 が掛かるのは**人数**ではなく**中継の有無**である。

### 定員を招待に載せた

塊の形を `[人数 1][鍵 32]*人数` から **`[定員 1][人数 1][鍵 32]*人数`** に変えた。

載せないと、受け取った側は**その会議が何人までなのか**を知らず、
外枠でしか数えられない。**送る側でも受け取る側でも数える**という M4 の約束
（**D15**）を、定員が可変になっても保つため。

受け取る側は 2 つを見る — **定員が外枠の内側か**、**人数が定員の内側か**。
テストで固定した（定員そのものを大きく名乗る偽の招待も弾く）。

### 既定は 12（2026-09-02・オーナー判断）

当初 4 で置いたが、「**規定 4 は少ない。12 くらいは欲しい**」との判断により **12** にした。

12 人フルメッシュで各自が負う帯域（`K×(N−1)`。**上下とも同じだけ掛かる**）:

| 画質 | 4 人 | **12 人** | 16 人（外枠） |
|---|---|---|---|
| 360p（0.6 Mbps） | 1.8 | **6.6** | 9.0 |
| 540p（1.0 Mbps） | 3.0 | **11.0** | 15.0 |
| 720p（1.5 Mbps） | 4.5 | **16.5** | 22.5 |
| 1080p（3.0 Mbps） | 9.0 | **33.0** | 45.0 |

**家庭用の光なら 720p まで届く。携帯回線と混み合った無線では落ちる。**

**AI 側は「実測前に既定を上げると、繋がらない会議が既定になる」と異議を出した。
オーナーはそれを踏まえて 12 と判断した。**そのまま従う（baseline §17 / §26）。

**残る risk はそのまま残す** — 12 人が手元の回線で成立するかは**まだ誰も確かめていない**。
M6（`issues/005`）で実測する。成立しなければ既定を下げるか、
画質を落とす（`K` を下げれば `N` は伸びる）。

### まだ実測していない

**12 も 16 も文献値のままである。**手元の回線で何人まで成立するかは M6 で実測する
（`issues/005`）。

### 覆してよい条件

- M6 の実測で、家庭用の回線で 16 人が成立しないと分かったとき → **外枠を下げる**
- 16 人を超える会議が必須になったとき → **そこは D7 の決着が先**（中継が要るため）
